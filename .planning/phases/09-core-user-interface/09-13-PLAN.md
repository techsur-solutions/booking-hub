<task type="auto">
  <name>Task 2: ApproveButton with conflict confirmation</name>
  <files>frontend/src/components/approval/ApproveButton.tsx</files>
  <action>
Create ApproveButton component accepting `booking` prop.

Click handler logic:

**If booking.conflict_flags.length === 0 (no conflicts):**
1. Show confirmation dialog: "Approve booking '{booking.title}'? This action cannot be undone."
2. On confirm: POST /bookings/:id/approve (from TechArch §4.2.5)
3. On 200 response: show toast "Booking approved", remove row from table (optimistic UI via onApproved callback to parent)

**If booking.conflict_flags.length > 0 (has conflicts):**
1. Show conflict confirmation dialog with two-step confirmation:
   - Header: "⚠️ Warning - Conflicts detected"
   - Body: "This booking conflicts with existing bookings:"
   - List conflicts (same format as ConflictBanner from 09-12): booking IDs, conflict types
   - Footer: "Approve anyway? This will create a double-booking."
   - Two buttons: "Cancel", "Approve Despite Conflicts"
2. On "Approve Despite Conflicts": POST /bookings/:id/approve
3. On 200 response: show toast "Booking approved (with conflicts)", remove row

From TechArch-BookingHub.md §4.2.5:
```typescript
POST /bookings/:id/approve
Response (200): { id: string; status: 'approved'; approved_at: string; approved_by: string; }
```

Button styling: Green button with checkmark icon. Always enabled (even for conflicts, since approvers can approve conflicts per UI-APPR-01).

Error handling:
- 404 booking not found → toast "Booking not found (may have been deleted)"
- 409 booking already approved/denied → toast "Booking already processed"
- 500 server error → toast "Failed to approve booking"

|-----------|----------|-----------|-------------|-----------------|
| T-09-13-01 | Elevation of privilege | Approve/deny without permission | mitigate | allowApproveBooking permission checked client-side for UI visibility (queue page gated), enforced server-side in POST /bookings/:id/approve and /deny (Phase 5); non-approver calling API directly returns 403 Forbidden |
| T-09-13-02 | Tampering | Denial reason injection | mitigate | Denial reason validated on backend: max length 500 chars, stored as plain text (no HTML rendering on display); XSS prevented via React's automatic escaping; no SQL injection (parameterized query) |
| T-09-13-03 | Repudiation | Approve/deny without audit trail | mitigate | Backend (Phase 5) logs approve/deny actions to audit_log table with approved_by/denied_by user ID and timestamp; immutable audit record per Phase 8 implementation; no repudiation possible |
| T-09-13-04 | Information disclosure | Queue enumeration | mitigate | GET /bookings?status=pending filtered by user's location access permissions on backend; approver only sees pending bookings for locations they manage; no global pending queue enumeration |
