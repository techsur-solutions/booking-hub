<objective>
Lay feeds-service's data-access, idempotency, RabbitMQ retry/DLQ, and shared-error-contract foundation — mirroring Phase 6's audit-log-service plan 06-03 EXACTLY, with one deliberate, load-bearing difference: NO security layer whatsoever. feeds-service is the single intentionally-public service in this architecture (F9.6, Phase 7 Success Criterion 3), so this plan adds no spring-security dependency, no SecurityConfig, no JWT re-validation.

Purpose: Y3-integrations.md mandates idempotent consumption for feeds-service's projection updater exactly as it does for notifications/audit-log, but the already-applied V1 DDL (TechArch §3.3) gave feed_bookings no idempotency tracking. This plan closes that gap additively before any consumer logic depends on it, and establishes the same retry/DLQ posture the other consumers have — so plan 07-02 (consumers) and plan 07-03 (public endpoints) build on proven infrastructure.
Output: A public, idempotency-ready, retry/DLQ-configured feeds-service scaffold with the FeedBooking entity/repository and shared error contract, ready for plan 07-02 to add the 2-queue projection consumer and plan 07-03 to add the 4 public feed endpoints.

**Named decision (idempotency dedup mechanism — processed_events table, not an upsert-only approach):** Y3-integrations.md offers two options — "an ON CONFLICT DO NOTHING upsert OR a processed-keys lookup table." feeds-service MUST use a **processed_events lookup table**, NOT upsert-only, because its projection is not a simple append: a single booking's lifecycle produces MULTIPLE distinct events (created → approved → updated → deleted) that each legitimately mutate or remove the SAME feed_bookings row by booking_id. An upsert keyed on booking_id cannot distinguish "legitimate second event for this booking" from "redelivery of an already-processed event" — only a dedup key on the event's own idempotency_key can. This mirrors notifications-service's and audit-log-service's lookup-first precedent (Phase 6), keyed the same way. This is an ADDITIVE V2 Flyway migration (CREATE TABLE processed_events) touching no V1 object, following the established convention of every service adding its own V2 in the phase that needs it (Phase 3, 4, 5, 6 all did).

**Named decision (NO security — the deliberate public exception):** Every other backend service in this project is Tier-2 JWT-secured and fails closed (503) on JWKS outage. feeds-service is the explicit exception: F9.6 and Phase 7 Success Criterion 3 require all 4 feed formats to be fully public — zero login, account, or token. This is already implemented platform-side (api-gateway SecurityConfig has `.pathMatchers("/feeds/**").permitAll()`, and the feeds-service scaffold pom.xml deliberately omits security deps). This plan HONORS that: it adds NO spring-security, NO oauth2-resource-server, NO SecurityConfig, NO CurrentUserProvider. The TechArch's "allowAPI (pending F0 default-public confirmation)" annotations are SUPERSEDED by F9.6's confirmation that feeds are public — this plan does not implement allowAPI gating.
</objective>
