<objective>
Build the four public feed endpoints on plan 07-01's FeedBooking repository, reading the projection plan 07-02 keeps current. This plan delivers the user-facing outcome of Phase 7: a reception desk, a visitor, or a lobby signage screen can see approved upcoming room bookings with zero login, in whatever format suits them (RSS reader, calendar subscription, JSON widget, or a full-screen auto-refreshing board).

Purpose: This is where Phase 7's goal becomes observably true. The critical design property is a SINGLE shared query path (FeedQueryService) that all four renderers call — this is what makes Success Criterion 3's "access rules are identical across all four formats" structurally true rather than something to re-verify format by format: there is only one access rule (none) and one filter rule (approved + upcoming + optional location), in one place.
Output: Four working public GET endpoints, each proven by integration test to be unauthenticated, to show only approved-upcoming bookings, to filter by location consistently (unknown->empty, malformed->400), and to emit the correct content type and cache headers.

**Named decision (hand-build RSS2 and iCal, add NO dependency):** The planning context offered a choice — add ical4j/rome, or hand-build. This plan HAND-BUILDS both RSS2 XML and iCal ICS as simple, well-specified text formats, for three reasons: (1) this is the one internet-facing public service, so minimizing its dependency/attack surface has real value; (2) both formats are small and stable (RSS2 = channel + items; iCal = VCALENDAR + VEVENTs) — the subset feeds need is a few dozen lines of string building, far less code than wiring and version-managing a library; (3) it gives exact control over field escaping and output, which matters precisely because the inputs (booking titles, location names) are upstream-controlled strings that must be correctly escaped for XML and for iCal line-folding. JSON uses Jackson (already present via spring-boot-starter-web). Renderers take `List<FeedBookingSummary>` and return a String; they are pure, unit-testable, and framework-free.

**Named decision (display-board is a standalone kiosk HTML route, not wired into React nav):** TechArch §2.7/§2.9 explicitly describe the display board as "a full-screen, auto-refreshing route, typically loaded on a kiosk browser rather than via normal nav." It is therefore a server-rendered HTML string returned directly by this Java service (not a React component, not a page in the frontend app's nav tree) — the orphan-page/nav-wiring concern does not apply: by design it is reached by pasting its URL into a kiosk browser, exactly as the architecture intends. Auto-refresh is achieved with a `<meta http-equiv="refresh" content="60">` tag (and the same ?location_id= preserved in the refresh), the simplest mechanism that needs no client JS. The frontend's "public feed landing page" (TechArch §2.9) that LINKS to these feeds is a separate frontend concern, out of scope for this backend phase.
</objective>

`FeedQueryService.java` — `@Service`, injects `FeedBookingRepository`. ONE public method all four formats use:
```java
public List<FeedBookingSummary> getApprovedUpcoming(String locationIdParam) {
    Instant now = Instant.now();
    List<FeedBooking> rows;
    if (locationIdParam == null || locationIdParam.isBlank()) {
        rows = repo.findByStatusAndStartTimeGreaterThanEqualOrderByStartTimeAsc("approved", now);
    } else {
        UUID locationId;
        try {
            locationId = UUID.fromString(locationIdParam);
        } catch (IllegalArgumentException e) {
            throw new FeedLocationFilterInvalidException("location_id is not a valid UUID"); // 400, not 500
        }
        // well-formed-but-unknown location_id simply matches no rows -> empty list -> empty feed, HTTP 200 (Success Criterion 2)
        rows = repo.findByStatusAndLocationIdAndStartTimeGreaterThanEqualOrderByStartTimeAsc("approved", locationId, now);
    }
    return rows.stream().map(this::toSummary).toList();
}
```
`toSummary` maps a `FeedBooking` to `FeedBookingSummary` (nesting locationId/locationName into the LocationRef). This method is the single point where "approved", "upcoming (>= now)", "optional location", "unknown -> empty", and "malformed -> 400" all live — every format calls it, so the behavior is provably identical across all four (Success Criterion 3's "applied consistently").

Also compute a simple `ETag` helper here or in the controller (Task 3): an ETag derived from the max(updated_at) and row-count of the result, or a hash of the rendered body — keep it deterministic so an unchanged projection yields the same ETag (enables CDN/proxy caching per TechArch §2.7). State the chosen approach in the SUMMARY.

`Rss2Renderer.java` — standard RSS 2.0:
```
<?xml version="1.0" encoding="UTF-8"?>
<rss version="2.0"><channel>
  <title>Booking-Hub — Upcoming Approved Bookings</title>
  <link>/feeds/rss2</link>
  <description>Approved upcoming room bookings</description>
  <!-- one <item> per booking: -->
  <item>
    <title>{XML-escaped booking title}</title>
    <description>{XML-escaped: location name + start–end time}</description>
    <guid isPermaLink="false">{booking_id}</guid>
    <pubDate>{start_time as RFC-1123, e.g. Wed, 02 Oct 2026 14:00:00 GMT}</pubDate>
  </item>
</channel></rss>
```
Implement an `xmlEscape` helper (& < > " ') applied to ALL title/location text — critical because titles/names are upstream-controlled. pubDate uses `DateTimeFormatter.RFC_1123_DATE_TIME` on the start_time at UTC.

`ICalRenderer.java` — standard iCalendar, one VEVENT per booking:
```
BEGIN:VCALENDAR
VERSION:2.0
PRODID:-//Booking-Hub//Feeds//EN
CALSCALE:GREGORIAN
BEGIN:VEVENT
UID:{booking_id}@booking-hub
DTSTAMP:{now as yyyyMMdd'T'HHmmss'Z'}
DTSTART:{start_time as yyyyMMdd'T'HHmmss'Z'}
DTEND:{end_time as yyyyMMdd'T'HHmmss'Z'}
SUMMARY:{iCal-escaped title}
LOCATION:{iCal-escaped location name}
END:VEVENT
END:VCALENDAR
```
Lines MUST end with CRLF (`\r\n`) per RFC 5545. Implement an `icalEscape` helper escaping `\`, `;`, `,`, and newlines per RFC 5545 §3.3.11. Times are UTC "Z" basic format. (Keep it to these required VEVENT fields — UID/DTSTAMP/DTSTART/DTEND/SUMMARY/LOCATION — which is a valid, subscribable VEVENT; do not over-engineer RRULE/VALARM, feeds show individual approved bookings.)

`DisplayBoardRenderer.java` — a self-contained full-screen HTML page:
- `<head>` includes `<meta http-equiv="refresh" content="60">` (auto-refresh every 60s — the Success-Criterion-"auto-refreshing" mechanism, no client JS needed) and inline `<style>` for large, legible signage (big font, high contrast, full-viewport). If a locationId was supplied, the refresh must preserve it — simplest correct approach: omit the `url=` in the meta so it refreshes the CURRENT URL (which already carries ?location_id=), so no URL reconstruction is needed.
- `<body>` renders each booking as a large row/card: title, location name, start–end time (human-readable). HTML-escape all upstream text (reuse an escape helper). Render a friendly "No upcoming bookings" state when the list is empty (never a blank screen).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet→API | All four /feeds/* endpoints are INTENTIONALLY public (F9.6); the real concerns are (a) can a caller reach a write path (no), (b) can pending/denied bookings leak (no), (c) can upstream-controlled strings in a feed break the output format or inject into a consumer |
| db→render | booking titles and location names are upstream-controlled strings reflected into XML (RSS2), iCal text, and HTML (display-board) — each needs format-correct escaping or it becomes an injection/output-corruption vector |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-03-01 | Elevation of privilege | FeedController HTTP surface | mitigate | All four endpoints are @GetMapping only — NO @PostMapping/@PutMapping/@DeleteMapping exists anywhere in feeds-service; a public caller has read-only access by construction, verified by the `! grep @PreAuthorize/@Secured` check and the GET-only controller |
| T-07-03-02 | Information disclosure | all four renderers / FeedQueryService | mitigate | The single shared FeedQueryService query filters `status='approved' AND start_time >= now`, so pending/denied/past bookings never enter ANY renderer — verified by FeedControllerIntegrationTest scenarios 1–4 seeding pending/denied/past rows and asserting their absence from every format (defense in depth atop plan 07-02's projection-level removal) |
| T-07-03-03 | Tampering (output injection) | Rss2Renderer / ICalRenderer / DisplayBoardRenderer on upstream-controlled title/location text | mitigate | Each renderer applies format-correct escaping (XML entity-escape for RSS2, RFC-5545 backslash-escape for iCal, HTML entity-escape for display-board) to ALL title/location strings — verified by FeedRendererTest scenarios feeding `&`/`<`/`,`/`;` and asserting escaped output, so a malicious booking title cannot break the feed or inject markup into a consumer |
