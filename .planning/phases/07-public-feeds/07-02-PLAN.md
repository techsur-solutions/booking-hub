<objective>
Build feeds-service's projection consumer on plan 07-01's foundation: 2 @RabbitListener methods (one per already-declared queue — feeds.booking.q, feeds.location.q) that keep the feed_bookings projection correct and current, so the public endpoints (plan 07-03) always read a projection containing EXACTLY the approved upcoming bookings with fresh location labels.

Purpose: This is where Phase 7 Success Criterion 1's core guarantee becomes real, executable code — "pending and denied bookings never appear in any format." That guarantee lives HERE, in the projection state machine: a denied/deleted booking is physically removed from feed_bookings, so no feed renderer in plan 07-03 can ever accidentally surface it. The projection also solves the cross-service denormalization problem (feeds-service must show location NAMES but owns only location_ids in booking events and may never query locations-resources-service's database) via an event-fed location_names cache.
Output: A feeds-service that consumes both its queues idempotently, applies the correct lifecycle transition per routing key, keeps location_name denormalized and fresh, and dead-letters malformed events — all proven against real Testcontainers Postgres + RabbitMQ.

**Named decision (location_name denormalization via an event-fed cache — the cross-service read problem):** feed_bookings.location_name is NOT NULL (V1 DDL), but a `booking.*` event payload carries `location_id` only, NOT the location's name (booking-service doesn't own location names — confirmed from Phase 5's booking event payload shape). feeds-service may NEVER synchronously query locations-resources-service's database (database-per-service rule). The resolution: an ADDITIVE V3 `location_names` cache table (location_id -> name), populated from `location.updated` events (payload carries `id` + `name`, confirmed from Phase 4's LocationResponse). When a booking event arrives: look up the name in the cache; if present, use it; if absent (the location event hasn't arrived yet, or arrived before this consumer existed), store the placeholder string `"Location " + location_id` so the NOT NULL constraint is satisfied and the feed degrades gracefully rather than failing the write. A later `location.updated` then back-fills the real name across all that location's rows. On `location.deleted`: KEEP the last-known name in both the cache and existing feed_bookings rows (graceful degradation per F09 §Process + Phase 4's own soft-delete "last-known values" convention) — never blank it, never delete feed rows (a deleted location does not retroactively un-book an approved meeting).

**Named decision (lifecycle -> projection transition, deriving Success Criterion 1):** action_type is the routing-key suffix — `routingKey.substring(routingKey.lastIndexOf('.') + 1)` (so `booking.approved` -> `approved`). The routing key arrives on the inbound message via the `AmqpHeaders.RECEIVED_ROUTING_KEY` header (the standard Spring AMQP way to read the key the message was published with; the outbox publishers set it from the outbox row's `routing_key`, per the confirmed users-permissions `OutboxPublisher` precedent). The suffix maps to a transition:
- `booking.created` / `booking.updated` -> UPSERT the feed_bookings row from the payload (booking_id, title, location_id, resolved location_name, start_time, end_time, status-from-payload). A `created` event for a NOT-yet-approved booking writes a row with status="pending" — which is correct and harmless, because plan 07-03's queries filter `status='approved'`, so it is invisible until approved; keeping it lets a later `booking.updated` find a row to update.
- `booking.approved` -> set the row's status="approved" (upsert if somehow absent), making it feed-visible.
- `booking.denied` -> DELETE the feed_bookings row (a denied booking must never appear — Success Criterion 1).
- `booking.deleted` -> DELETE the feed_bookings row.
This makes "pending and denied never appear" structurally true at the projection level, not merely at the query level — defense in depth.
</objective>

```java
@Transactional
public void applyBookingEvent(String routingKey, JsonNode body) {
    String action = actionOf(routingKey); // created|updated|approved|denied|deleted
    UUID bookingId = UUID.fromString(body.get("id").asText());
    switch (action) {
        case "denied", "deleted" -> feedBookingRepository.deleteById(bookingId); // never appears in any feed
        case "approved" -> upsert(bookingId, body, "approved");
        case "created", "updated" -> upsert(bookingId, body, body.get("status").asText()); // status from payload (pending/approved)
        default -> { /* unknown booking action: log warn, no-op (never throw -> never poison) */ }
    }
}

@Transactional
public void applyLocationEvent(String routingKey, JsonNode body) {
    String action = actionOf(routingKey); // updated|deleted
    UUID locationId = UUID.fromString(body.get("id").asText());
    if ("updated".equals(action)) {
        String name = body.get("name").asText();
        LocationName cache = locationNameRepository.findById(locationId).orElseGet(LocationName::new);
        cache.setLocationId(locationId); cache.setName(name);
        locationNameRepository.save(cache);
        // back-fill every already-projected booking at this location so feed labels stay fresh
        feedBookingRepository.updateLocationName(locationId, name); // custom @Modifying query on the repo
    }
    // "deleted": deliberately KEEP last-known name in cache and in feed_bookings rows (graceful degradation).
}

private void upsert(UUID bookingId, JsonNode body, String status) {
    FeedBooking fb = feedBookingRepository.findById(bookingId).orElseGet(FeedBooking::new);
    UUID locationId = UUID.fromString(body.get("location_id").asText());
    fb.setBookingId(bookingId);
    fb.setTitle(body.get("title").asText());
    fb.setLocationId(locationId);
    fb.setLocationName(resolveLocationName(locationId)); // cache hit -> real name; miss -> "Location <uuid>" placeholder
    fb.setStartTime(Instant.parse(body.get("start_time").asText()));
    fb.setEndTime(Instant.parse(body.get("end_time").asText()));
    fb.setStatus(status);
    feedBookingRepository.save(fb);
}

private String resolveLocationName(UUID locationId) {
    return locationNameRepository.findById(locationId).map(LocationName::getName)
        .orElse("Location " + locationId); // graceful placeholder; a later location.updated back-fills the real name
}
```

`FeedEventConsumer.java` — `@Component`, injects `FeedProjectionService`, `ProcessedEventRepository`, `ObjectMapper`:
```java
@RabbitListener(queues = "feeds.booking.q")
public void onBookingEvent(Message message,
        @Header(name = "idempotency_key", required = false) String idempotencyKey,
        @Header(AmqpHeaders.RECEIVED_ROUTING_KEY) String routingKey) {
    process(message, idempotencyKey, routingKey, /*isBooking*/ true);
}

@RabbitListener(queues = "feeds.location.q")
public void onLocationEvent(Message message,
        @Header(name = "idempotency_key", required = false) String idempotencyKey,
        @Header(AmqpHeaders.RECEIVED_ROUTING_KEY) String routingKey) {
    process(message, idempotencyKey, routingKey, /*isBooking*/ false);
}

@Transactional
void process(Message message, String idempotencyKey, String routingKey, boolean isBooking) {
    if (idempotencyKey == null || idempotencyKey.isBlank()) {
        throw new MissingIdempotencyKeyException("event missing idempotency_key header, routing_key=" + routingKey);
        // non-retryable (plan 07-01's RabbitConfig) -> straight to feeds.*.q.dlx -> *.dlq, never silently dropped
    }
    UUID key = UUID.fromString(idempotencyKey);
    if (processedEventRepository.existsByIdempotencyKey(key)) {
        return; // duplicate redelivery -> safe no-op ack, projection never double-applied
    }
    JsonNode body = objectMapper.readTree(message.getBody());
    if (isBooking) projectionService.applyBookingEvent(routingKey, body);
    else           projectionService.applyLocationEvent(routingKey, body);
    ProcessedEvent pe = new ProcessedEvent(); pe.setIdempotencyKey(key);
    processedEventRepository.save(pe); // same transaction as the projection mutation -> atomic
}
```
The lookup-first check (check `existsByIdempotencyKey` BEFORE applying, not insert-then-catch-violation) is deliberate: plan 07-01's `rabbitListenerContainerFactory` retry interceptor re-invokes this ENTIRE method on a transient failure, so an insert-first/catch-duplicate approach would misfire on its own retry (the retry would see its own first-attempt insert as a "duplicate"). The `processed_events` PK (plan 07-01) is the final race-safe backstop against true concurrent redelivery across threads. Keep the `@Transactional` boundary around BOTH the projection mutation AND the processed_events insert so a crash between them rolls back cleanly and the event safely redelivers.
