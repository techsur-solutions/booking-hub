**Final Integration & UAT Verification:**

## 1. Full-Stack Smoke Test
**Goal**: Verify complete end-to-end workflow from login to booking approval.

**Steps:**
1. Start full stack: `docker-compose up -d` (all backend services + frontend)
2. Wait for services healthy: `docker-compose ps | grep healthy`
3. Open browser to `http://localhost:3000`

**Smoke Test Flow:**
- **Login**: Navigate to `/login`, enter test credentials, assert redirect to calendar
- **Create Booking**: Click empty calendar slot, fill form (title, location, resource, custom field), save
- **Verify Status**: Check booking status badge (Pending or Approved based on settings)
- **Approve Booking** (if pending): Navigate to Approval Queue, approve booking
- **Verify in Calendar**: Return to Calendar View, verify booking appears with correct colour, conflict badge (if present)
- **Edit Booking**: Click booking, click Edit, change title, save, verify updated
- **Delete Booking**: Click Delete, confirm, verify removed from calendar

**Success signal**: Full flow completes without errors, data persists across refreshes, backend APIs respond correctly.

## 2. Cross-Browser Testing
**Goal**: Verify UI works correctly in Chrome, Firefox, Safari, Edge.

**Test matrix:**
| Browser | Version | Platform | Test Result |
|---------|---------|----------|-------------|
| Chrome | Latest | macOS/Windows | ☐ Pass |
| Firefox | Latest | macOS/Windows | ☐ Pass |
| Safari | Latest | macOS | ☐ Pass |
| Edge | Latest | Windows | ☐ Pass |

**For each browser:**
1. Open `http://localhost:3000`
2. Login
3. Navigate to Calendar, Day, List views (verify rendering)
4. Create booking (verify form submission)
5. Navigate to admin screens: Locations, Resources, Custom Fields, Users, Settings (verify table/form rendering)
6. Test responsive breakpoints: Resize window to 1920px (desktop), 768px (tablet), 375px (mobile)
7. **Document any browser-specific issues** (CSS rendering differences, JS errors, etc.)

**Success signal**: Core functionality works in all 4 browsers, no critical rendering issues.

## 3. Performance Benchmarks
**Goal**: Verify acceptable load times and responsiveness.

**Use Chrome DevTools Performance tab or Lighthouse:**

**Metrics to measure:**
- **Initial page load** (from cold start to interactive):
  - Target: <3 seconds on 3G Fast connection
  - Measure: Open incognito window, navigate to `/login`, record Time to Interactive
- **Calendar view render** (large dataset with 100+ bookings):
  - Target: <1 second from route navigation to visible events
  - Measure: Navigate to `/bookings?view=month`, record render time
- **Admin table load** (e.g., Locations Admin with 50+ locations):
  - Target: <1 second from route navigation to visible table
  - Measure: Navigate to `/admin/locations`, record table render time

**Performance optimization checklist:**
- [ ] Production build is minified (`npm run build` produces optimized bundle)
- [ ] Code splitting implemented (React.lazy for route-level chunks)
- [ ] Images optimized (compressed, appropriate formats)
- [ ] API responses cached where appropriate (React Query/SWR stale-while-revalidate)
- [ ] No unnecessary re-renders (React DevTools Profiler shows efficient component updates)

**Success signal**: Initial load <3s, calendar render <1s, admin tables <1s, no performance red flags in Lighthouse.

## 4. Production Readiness Checklist
**Goal**: Verify all production requirements met.

**Checklist:**
- [ ] **No console errors** in production build (open DevTools Console, navigate app, verify 0 errors)
- [ ] **No console warnings** (except known third-party library warnings)
- [ ] **Environment variables** correctly configured for production (API URLs, Keycloak endpoints)
- [ ] **Error boundaries** catch and display errors gracefully (test by triggering error, verify user-friendly error page)
- [ ] **Loading states** present for all async operations (API calls show loading spinner/skeleton)
- [ ] **Empty states** present for all lists/tables (e.g., "No locations found" when table empty)
- [ ] **404 page** renders for unknown routes (navigate to `/nonexistent-route`)
- [ ] **CI tests pass** (GitHub Actions E2E workflow shows green check)
- [ ] **Accessibility audit** passes (Plan 10-11 checklist complete, axe-core tests pass)
- [ ] **Documentation** complete and accurate (end-user guide, admin guide, inline tooltips)

**Success signal**: All checklist items pass, no critical issues found.

## 5. User Acceptance Testing (UAT)
**Goal**: Verify application meets user expectations from JOURNEYS-BookingHub.md personas.

**Persona-based UAT scenarios:**

**Maya (End User) — JRN-01 "Book a room with resources":**
- Can she discover an open slot in Calendar View?
- Can she create a booking with resources and custom fields in <2 minutes?
- Does she receive clear conflict feedback if slot is taken?
- Does she see explicit status confirmation (Pending/Approved)?

**David (Approver) — JRN-02 "Morning pending-queue review":**
- Can he see all pending bookings in Approval Queue?
- Are conflict badges visible inline (no need to click each booking)?
- Can he approve/deny with one click + confirmation?
- Does conflicted approval require explicit confirmation?

**Priya (Admin) — JRN-03 "Onboard new location":**
- Can she add a location in <5 minutes?
- Is the form single-page (not multi-step wizard)?
- Does colour picker work intuitively?
- Does immediate propagation indicator appear after saving settings?

**Jordan (Public Viewer) — JRN-04 "Check kiosk display":**
- Does Display Board show only approved bookings?
- Is "Approved-Only" guarantee visually evident?
- Does board auto-refresh every 60 seconds?

**Success signal**: All 4 persona scenarios complete successfully, users report satisfaction with workflows.
