<objective>
Implement booking create/edit/delete/clone with the full legacy field set, recurring bulk-create, and — the single most important decision in this phase — resolve a genuine 3-way contradiction in this project's own authoritative documents about conflict-enforcement policy.

**THE CONFLICT-ENFORCEMENT-POLICY DECISION.** Three sources disagree:
1. **FRD F2 §Process step 6 / §Terminology** (pre-audit interim assumption, explicitly marked "pending final F0 confirmation"): permission-conditional — hard block (409) without `allowApproveBooking`, soft warning with it.
2. **F0 audit, `open-questions.md` item #2 (RESOLVED AS FACT about legacy, ground truth):** this permission-conditional premise does not exist anywhere in legacy code. Legacy's ONE mechanism (`Bookings.check()`) is unconditionally non-blocking for EVERY user regardless of permission — `create()`/`update()` perform NO server-side conflict validation at all; a clashing booking always saves. F0's own text: *"Whether the new system should hard-block for all users... or replicate the legacy's always-non-blocking behavior is a product decision this planning agent is not authorized to make"* — explicitly escalated to this phase.
3. **TechArch §1.5 Architectural Decision Log (the project's own post-audit resolution):** explicitly REJECTED the permission-conditional split and chose **"Hard block (HTTP 409) for ALL roles, interim, until F0 confirms otherwise"** as a single, uniform code path — reasoning that legacy gave no basis for inventing a new permission-conditional split.

ROADMAP's own Success Criterion 4 for this phase repeats source #1's wording verbatim, seemingly copied from the FRD before TechArch's §1.5 override was written, never reconciled.

**DECISION: implement the ROADMAP's literal wording — permission-conditional (hard block for callers without `role_booking_approver`, soft warning for callers with it).** Rationale: the ROADMAP is this specific phase's own current, most-specific directive, and explicitly repeats the permission-conditional framing as its Success Criterion 4, not TechArch's uniform-hard-block override. This DIVERGES from TechArch §1.5's documented decision — flagged here explicitly so a future documentation pass can reconcile TechArch §1.5 to match (recommended correction: update TechArch §1.5's row to record the permission-conditional policy as final, citing this plan). Neither policy is legacy parity — F0 confirmed legacy never blocks ANYONE — so this is new product design either way, and the permission-conditional shape is the one actually chosen here, by this plan, for this codebase, now.

Purpose: This plan is where ROADMAP Success Criteria 1, 3, 4, and 5 (bypass-approve stage) become real, callable behavior, built directly on plan 05-02's single conflict-evaluation engine.
Output: `POST /bookings` (single + recurring series), `PUT /bookings/{id}`, `DELETE /bookings/{id}`, `POST /bookings/{id}/clone` — all enforcing the policy above through exactly one shared application call site.
</objective>
