<objective>
Build the single, shared conflict-detection engine every later plan calls — ConflictDetectionService, implementing TechArch's exact indexed half-open-interval query shapes for both location-level and resource-level overlap, with is_unique-aware resource filtering — plus the three synchronous outbound HTTP clients booking-service needs (locations-resources-service, custom-field-service, settings-service), each using token relay, and the standalone `POST /bookings/check-conflicts` endpoint.

Purpose: Per ROADMAP Success Criterion 4 and TechArch §2.2, there must be exactly ONE conflict-evaluation code path, shared identically by create, edit, bulk calendar/list reads, and this standalone endpoint. Building it in its own plan — BEFORE the create/edit plan (05-03) and the approval/read plan (05-04), which both consume it in the same later wave — guarantees neither of those plans has to invent its own copy or coordinate a simultaneous first-write to this file.
Output: `ConflictDetectionService` (pure, local-database-only, zero outbound HTTP calls inside it), three tested outbound clients, and a working `POST /bookings/check-conflicts` endpoint — ready for plans 05-03/05-04 to call without touching this plan's files.
</objective>

**Named decision — ConflictDetectionService has ZERO cross-service HTTP dependencies, by design.** TechArch's own framing describes it as "an internal Booking Service function" querying only tables this service owns ("No dedicated table; queries the `bookings` and `booking_resources` tables owned by the Booking Service"). The `is_unique`-awareness this phase's brief requires (only check resource-level conflicts for resources where `is_unique=true`, per F0's Resource-model finding, `findings/02-reference-data.md`, already established by Phase 4) is therefore implemented as a CALLER responsibility, not inside this service: the caller (plan 05-03's `BookingWriteService`, plan 05-04's `BookingReadService`, and this plan's own `ConflictController`) resolves each resource's `is_unique` flag via `LocationsResourcesClient` FIRST (a call it already needs to make anyway, for location/resource existence validation), filters the resource id list down to only the unique ones, and passes that pre-filtered list in. This keeps `ConflictDetectionService` maximally simple, fast, and independently testable with zero mocking of external services.

**F0 point 3 (open-questions.md #3, multi-resource conflict scope) — RESOLVED by TechArch's own already-specified design, applied here.** F0's audit left legacy's resource-level enforcement mechanism unconfirmed (the code wasn't in that audit plan's file set) and flagged the multi-resource conflict SCOPE question as open. TechArch §3.3 already resolved it with a concrete design this task implements verbatim: each attached resource is checked INDEPENDENTLY via its own resource-level query, and the booking's full conflict result is the UNION of the location-level result and every per-resource result (see the per-resource loop below). This is the explicit resolution of a legacy ambiguity, not a parity claim — legacy's own resource-conflict mechanism was a separate, unconfirmed, admin-gated AJAX endpoint (see F0 point 5 immediately below), not a confirmed query this project could replicate.

**F0 point 5 (open-questions.md #15, legacy's own resource-level conflict mechanism) — deliberately NOT replicated structurally, per Phase 4's own precedent.** F0 found legacy's resource-conflict check was a separate, fragmented, oddly admin-gated AJAX endpoint (`Resources.cfc::checkavailability`, gated behind admin-only `accessresources` — a confirmed design-smell F0 named explicitly, already flagged out-of-scope by Phase 4 plan 04-02's own Task 2: "This phase does NOT implement any `checkavailability`-equivalent endpoint... that belongs entirely to Phase 5's booking-service conflict detection, which will read this service's `is_unique`/`restrict_locations` fields... via the plain `GET /resources`/`GET /resources/{id}` read endpoints"). This plan is that promised consumer: `ConflictDetectionService` queries ONLY this service's own `bookings`/`booking_resources` tables (point 3's resolution above), consulting `LocationsResourcesClient` solely for the `is_unique` flag via a plain read call — never calling or replicating legacy's fragmented `checkavailability` endpoint shape.

Add to `BookingResourceRepository` (additive, same file):
```java
@Query(value = """
    SELECT br.booking_id FROM booking_resources br
    JOIN bookings b ON b.id = br.booking_id
    WHERE br.resource_id = :resourceId
      AND b.deleted_at IS NULL
      AND b.status <> 'denied'
      AND b.id <> COALESCE(:excludeBookingId, '00000000-0000-0000-0000-000000000000'::uuid)
      AND b.start_time < :proposedEndTime
      AND :proposedStartTime < b.end_time
    """, nativeQuery = true)
List<UUID> findConflictingBookingIdsByResource(@Param("resourceId") UUID resourceId,
    @Param("proposedStartTime") Instant proposedStartTime, @Param("proposedEndTime") Instant proposedEndTime,
    @Param("excludeBookingId") UUID excludeBookingId);
```
**Named implementation choice:** this is called ONCE PER resource id in a loop (not a single `= ANY(:resourceIds)` array-bound query) — simpler and safer with plain JPA native queries (Postgres UUID-array JDBC binding is awkward without a custom type), and produces the IDENTICAL union-of-per-resource-results TechArch's own text describes ("each attached resource is checked independently... the booking's full conflict result is the UNION of the location-level result and every per-resource result").

`ConflictDetectionService.java` — `@Service`, injects `BookingRepository`, `BookingResourceRepository`:
```java
public ConflictCheckResult checkConflicts(UUID locationId, List<UUID> uniqueResourceIds, Instant proposedStart, Instant proposedEnd, UUID excludeBookingId)
```
1. If `locationId != null`: run `findConflictingBookingIdsByLocation`, map each returned id to a `ConflictFlag(id, "location", locationId, null)`.
2. For each id in `uniqueResourceIds` (already pre-filtered to `is_unique=true` resources by the caller — see named decision above): run `findConflictingBookingIdsByResource`, map each returned id to `ConflictFlag(id, "resource", null, resourceId)`.
3. Concatenate both lists (the UNION, per TechArch) into `conflicts`; `hasConflict = !conflicts.isEmpty()`.
4. This method NEVER throws, NEVER enforces anything, NEVER checks the caller's role — it is a pure, side-effect-free query. Enforcement (hard-block vs. soft-warning) is a SEPARATE, single call site plan 05-03 adds around this method's result — not duplicated here, not duplicated in plan 05-04's read-only bulk-flagging use either (which never enforces at all, only displays).

- A soft-deleted booking that would otherwise overlap → excluded.
- An edit scenario (`excludeBookingId` = the booking's own id) against its own unchanged time range → NO self-conflict.
- Two bookings sharing a resource id with overlapping times → resource conflict detected (test calls `checkConflicts` with that resource id already in the `uniqueResourceIds` list, simulating the caller having already resolved `is_unique=true`).

`LocationsResourcesClient.java` — `@Service`, injects the RestClient bean + `CurrentUserProvider`:
- `Optional<LocationResponse> getLocation(UUID id)` — `GET /locations/{id}` with `Authorization: Bearer ${currentUserProvider.getRawBearerToken()}`. Per Phase 4 plan 04-02's named decision, this endpoint returns `200` with last-known values even for a soft-deleted id (`deletedAt` populated) and `404` ONLY for a genuinely nonexistent id. Maps `404` → `Optional.empty()`; any other non-2xx propagates as a generic runtime exception (caller decides how to translate it — see Task 3).
- `Optional<ResourceResponse> getResource(UUID id)` — same pattern, `GET /resources/{id}`, exposing `isUnique`/`restrictLocations` for plan 05-03/05-04's is_unique-filtering logic (feeding `ConflictDetectionService`'s `uniqueResourceIds` parameter).
- **Named decision — why token relay, not a dedicated service-account credential, is sufficient here:** locations-resources-service's own Tier-2 config (Phase 4 plan 04-01) gates GET by `role_calendar_viewer` — a BROAD baseline "can see the calendar/reference-data at all" gate, directly mirroring legacy's own `accesscalendar` filter which stacked underneath EVERY Bookings-controller action (F0 findings/01-booking-core.md: "applies to every action in this controller, no exceptions"). Any real user capable of reaching a booking action is expected to also hold `role_calendar_viewer` as part of normal Keycloak role provisioning (the identical convention Phase 2's seed admin user already demonstrates — holding all 11 roles together). This is NOT the same class of problem as the custom-field-service gap below (an admin-only management role with zero conceptual overlap with "can create a booking") — it is a correctly-scoped broad-read role Phase 4 already designed for exactly this kind of cross-service consumption.

`SettingsClient.java` — `@Service`, injects the RestClient bean + `CurrentUserProvider`:
- `boolean getApproveBookingFlag()` — `GET /settings` with relayed token (settings-service requires NO specific role for GET, per Phase 4 plan 04-06 — any authenticated caller). **Named decision — 5-second local cache, per TechArch §1.5's explicit architectural decision** ("synchronous read, with a short-TTL local cache (5s) in booking-service... `approveBooking` is read exactly once per booking creation... a stale cache for a few seconds has no correctness impact"): implement via a simple `volatile` field holding `(SettingsResponse value, long fetchedAtEpochMillis)`, re-fetching only when `System.currentTimeMillis() - fetchedAtEpochMillis > 5000`. No new caching library dependency needed for a single cached value.
- On any connection failure/timeout/non-2xx response: throw `ApprovalSettingsUnavailableException` (503, from plan 05-01) — matching the FRD's explicit "Settings Service unavailable when reading approveBooking at creation time" error state exactly.

`CustomFieldClient.java` — `@Service`, injects the RestClient bean + `CurrentUserProvider`:
- `List<CustomFieldDefinition> getApplicableFields(UUID contextId)` — `GET /custom-fields?context_id={contextId}` with relayed token.
- **Named decision — resolving the confirmed custom-field-service Tier-2 integration gap, OPTION (b) chosen explicitly.** Phase 4 plan 04-04's `CustomFieldController` gates EVERY method — including this read-only applicability query — behind `role_customfield_admin` uniformly, with no broader-read carve-out (unlike locations-resources-service, which correctly split `role_calendar_viewer`-read vs. `role_location_admin`-write). Since service-to-service calls never transit the Gateway (ClusterIP-to-ClusterIP, internal-only, per TechArch §5.4), custom-field-service's OWN Tier-2 check is the sole enforcement point on this path, and it WILL reject any booking-creating caller's relayed token that lacks `role_customfield_admin` — which is the normal case for an ordinary booking creator. **Chosen resolution: option (b), graceful degradation, not option (a) (amending 04-04-PLAN.md) or option (c).** Rationale: amending Phase 4's plan would also require updating its `Tier1Tier2ConsistencyTest` (which explicitly asserts "every endpoint — including GETs — requires role_customfield_admin" as a named must-have) and would touch a phase outside this one's declared scope for a benefit this phase's own success criteria do not require (custom field VALUE persistence/validation is not among ROADMAP's 5 success criteria for Phase 5, and F5 is not in this phase's mapped requirements F1/F2/F3). Implementation: catch `HttpClientErrorException.Forbidden` (403) OR any other HTTP/connectivity failure from this call, log a warning naming the known gap, and return `List.of()` (empty) rather than propagating the failure. **Concrete, named consequence of this choice:** when a normal booking creator's relayed token lacks `role_customfield_admin` (the expected case), any `custom_field_values[]` the client submitted on that booking are NOT validated against field-definition applicability — plan 05-03 still PERSISTS them as submitted (trusting the client), it simply cannot cross-check `field_id` legitimacy in this failure scenario. This is an accepted, explicitly-named degradation, not a silent gap — see this plan's threat model.
