```sql
-- F0 schema completion (findings/01-booking-core.md, Event model registerSystemFields()):
-- TechArch's V1 DDL (Phase 2 plan 02-01, already executed) covers only title/location_id/
-- start_time/end_time/status + workflow columns + series_id. These six additional confirmed
-- legacy Event fields were omitted entirely from TechArch's placeholder schema.
ALTER TABLE bookings ADD COLUMN all_day BOOLEAN NOT NULL DEFAULT false;
ALTER TABLE bookings ADD COLUMN description TEXT NULL;
ALTER TABLE bookings ADD COLUMN layout_style VARCHAR(255) NULL;
ALTER TABLE bookings ADD COLUMN contact_name VARCHAR(255) NULL;
ALTER TABLE bookings ADD COLUMN contact_email VARCHAR(320) NULL;
ALTER TABLE bookings ADD COLUMN contact_no VARCHAR(50) NULL;

-- Named decision: `emailcontact` is explicitly NOT added as a column here. F0 confirmed it is a
-- transient, request-only virtual flag read exactly once by Bookings.create()'s email-trigger
-- check and never referenced in update() or anywhere else. It is carried as a field on
-- BookingCreateRequest (plan 05-03) and in the booking.created event payload only — never
-- persisted. Do not add an email_contact column.

-- Named decision 2 (closes the custom_field_values DB-ownership contradiction): TechArch §2.4/
-- §1.5 states "booking-service persists custom_field_values rows itself" while TechArch §3.3
-- declares the custom_field_values table owned by custom-field-service's OWN database
-- (customfld_db), with a live FK to custom_fields(id) WITHIN that database. Phase 2's already-
-- executed database-per-service decision (Success Criterion 2: "no shared schema and no cross-
-- service database connection string") makes the literal TechArch instruction architecturally
-- impossible — booking-service has no connection string into customfld_db and must not be given
-- one. Resolution: booking-service owns a LOCAL table in its own booking_db, referencing
-- custom_field_id by UUID only (a cross-service reference — the identical pattern already
-- established for location_id/resource_id in this same table), validated not via a DB-level FK
-- but via a synchronous call to custom-field-service's applicability endpoint (plan 05-02). This
-- preserves TechArch's actual intent (booking-service owns and writes this data) while fixing the
-- self-contradictory DDL placement.
CREATE TABLE booking_custom_field_values (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    booking_id      UUID NOT NULL REFERENCES bookings(id) ON DELETE CASCADE,
    custom_field_id UUID NOT NULL,                    -- cross-service reference to custom-field-service; no FK (different database)
    value           TEXT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_booking_custom_field UNIQUE (booking_id, custom_field_id)
);
CREATE INDEX idx_booking_custom_field_values_booking ON booking_custom_field_values (booking_id);

-- Transactional outbox (same pattern as every other service in this project: Phase 3 plan 03-01,
-- Phase 4 plans 04-01/04-03/04-05). Written in Task 1 here (not a later plan) specifically so the
-- scheduled relay bean exists and is independently testable BEFORE any business-logic plan writes
-- to it — plans 05-03 and 05-04 run in the SAME wave in parallel and both need to publish outbox
-- rows; whichever created OutboxPublisher.java first would create a file-ownership race. Centralizing
-- it here, proven against a directly-inserted row (not a controller-created one), avoids that race
-- entirely.
CREATE TABLE outbox (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    aggregate_type  VARCHAR(64) NOT NULL,              -- 'booking'
    aggregate_id    UUID NOT NULL,
    exchange        VARCHAR(100) NOT NULL,              -- 'booking.events' (already declared, Phase 2 plan 02-09)
    routing_key     VARCHAR(100) NOT NULL,              -- 'booking.created' | 'booking.updated' | 'booking.deleted' | 'booking.approved' | 'booking.denied'
    idempotency_key UUID NOT NULL DEFAULT gen_random_uuid(),
    payload         JSONB NOT NULL,
    status          VARCHAR(16) NOT NULL DEFAULT 'pending',
    attempt_count   INTEGER NOT NULL DEFAULT 0,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    published_at    TIMESTAMPTZ NULL
);
CREATE INDEX idx_outbox_pending ON outbox (status, created_at) WHERE status = 'pending';
CREATE UNIQUE INDEX uq_outbox_idempotency_key ON outbox (idempotency_key);
```

**Named decision — 2 error codes added beyond the FRD's catalogue, both required for this phase's own explicitly-chosen behavior:**
- `BookingNotFoundException` → 404, `BOOKING_NOT_FOUND` — the FRD's F1 error table never enumerates a plain "booking id not found" case for `GET/PUT/DELETE /bookings/{id}` (it only names `BOOKING_SOURCE_NOT_FOUND` for clone and `APPROVAL_BOOKING_NOT_FOUND` for approve/deny, leaving ordinary CRUD lookups uncovered) — added here to fill that gap, kept distinct from the other two so each entry point's error stays unambiguous about which action failed.
- `BookingForbiddenException` → 403, `BOOKING_FORBIDDEN` — required by TechArch §4.2's own API table, which specifies `PUT/DELETE /bookings/{id}` as **"`allowRoomBooking` (owner) or admin"** — an ownership restriction with no corresponding FRD error code. Used both by `BookingAccessDeniedHandler` (Task 3, caller holds no booking role at all) and manually thrown by plan 05-03's `BookingWriteService` (caller holds `role_booking_creator` but is not the booking's owner, and does not hold `role_booking_approver` either).

**Named decision — generic Bean Validation handler, matching Phase 4's precedent.** The FRD's error tables do not catalogue a code for malformed DTO shapes (e.g., an unparseable `recurrence` pattern, a non-ISO datetime string). Rather than inventing ad-hoc codes, `GlobalExceptionHandler.java` adds a SECOND `@ExceptionHandler(MethodArgumentNotValidException.class)` method (additive to the primary `ApiException` handler) producing a 400 `ApiError` with `error_code="REQUEST_MALFORMED"` — the FRD's own platform-level cross-cutting code (TechArch §4.12), exactly as Phase 4 plan 04-04 established for this same class of problem.

`GlobalExceptionHandler.java` — `@RestControllerAdvice` with: (a) one `@ExceptionHandler(ApiException.class)` method covering all 12 subtypes polymorphically, building an `ApiError` from the caught exception's `httpStatus`/`errorCode`/`message` + current request path + `Instant.now()`; (b) the `MethodArgumentNotValidException` → `REQUEST_MALFORMED` handler described above.

Add to `application.yml`:
```yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: http://${KEYCLOAK_HOST:localhost}:${KEYCLOAK_PORT:8180}/realms/${KEYCLOAK_REALM:bookinghub}
```

**Named decision — Tier-2 role split, narrower than the Gateway's coarse Tier-1 gate (never weaker, per the two-tier model).** The Gateway's already-executed Tier-1 route table (`services/api-gateway/src/main/java/com/bookinghub/gateway/config/SecurityConfig.java`) applies ONE coarse rule to ALL methods on `/bookings/**`: `hasAnyAuthority("SCOPE_role_booking_viewer", "SCOPE_role_booking_creator", "SCOPE_role_booking_approver")` — no per-HTTP-method distinction at all (unlike `/locations/**`/`/resources/**`, which the Gateway already splits by method). This plan's Tier-2 layer narrows that coarse gate per-action, per TechArch §4.2's exact permission column:
- `POST /bookings`, `POST /bookings/{id}/clone`, `POST /bookings/check-conflicts` → `role_booking_creator`
- `GET /bookings`, `GET /bookings/{id}` → any of `role_booking_viewer` / `role_booking_creator` / `role_booking_approver` (matches legacy's `list`/`view` needing only the read-oriented flag, broadened since creators/approvers obviously need to see bookings too — F0 findings/01-booking-core.md's gate table)
- `PUT /bookings/{id}`, `DELETE /bookings/{id}` → `role_booking_creator` (own bookings only, code-level ownership check — not expressible as a static `@PreAuthorize` role string, enforced manually in plan 05-03's `BookingWriteService`) OR `role_booking_approver` (any booking) — per TechArch §4.2's explicit "(owner) or admin" text, a deliberate tightening beyond confirmed legacy's flat ownerless permission model (F0 findings/01-booking-core.md confirmed legacy's `update()`/`delete()` have NO ownership check at all)
- `POST /bookings/{id}/approve`, `POST /bookings/{id}/deny` → `role_booking_approver`

Every one of these Tier-2 role requirements is a SUBSET of the Gateway's 3-role Tier-1 gate, never a role outside it — this is what "stricter, never weaker" means here, and is what `Tier1Tier2ConsistencyTest` below proves.

`SecurityConfig.java` — `@EnableWebSecurity @EnableMethodSecurity` + `SecurityFilterChain`:
```java
.authorizeHttpRequests(auth -> auth
    .requestMatchers("/actuator/health/**").permitAll()
    .anyRequest().authenticated())
.oauth2ResourceServer(oauth2 -> oauth2
    .jwt(Customizer.withDefaults())
    .authenticationEntryPoint(jwksOutageAuthenticationEntryPoint))
.exceptionHandling(ex -> ex
    .authenticationEntryPoint(jwksOutageAuthenticationEntryPoint)
    .accessDeniedHandler(bookingAccessDeniedHandler))
```
Controller methods (built in plans 05-02/05-03/05-04) carry the actual per-action role requirement via `@PreAuthorize`, per the named decision above.

`JwksOutageAuthenticationEntryPoint.java` — identical pattern to every prior-phase service: implements `AuthenticationEntryPoint`, inspects the cause chain for a network-class JWKS-connectivity failure (`ConnectException`/`UnknownHostException`/`TimeoutException`) → 503 `ApiError` (`SERVICE_UNAVAILABLE`); otherwise → 401 `ApiError` (`AUTH_UNAUTHENTICATED`).

`BookingAccessDeniedHandler.java` — implements `AccessDeniedHandler`. Fires when an authenticated caller's `@PreAuthorize` role check fails — writes HTTP 403 with `ApiError` (`error_code="BOOKING_FORBIDDEN"`, the named addition from Task 2). **Note:** the APPROVE/DENY actions use the FRD-named `APPROVAL_FORBIDDEN` code instead, which — like Phase 3's `PermissionController` precedent — requires a manual `hasRole(...)` check inside `BookingApprovalController` (plan 05-04) throwing `ApprovalForbiddenException` directly rather than relying on this generic filter-chain handler, so the FRD's distinct code is preserved for that specific action pair. Every other controller (create/edit/delete/clone/read/check-conflicts) uses plain `@PreAuthorize` and falls through to this generic handler correctly.

`CurrentUserProvider.java` — `@Component`:
```java
UUID getCurrentUserId()        // from SecurityContextHolder's Jwt principal's "sub" claim
Set<String> getCurrentRoles()  // from "realm_access.roles"
boolean hasRole(String role)
String getRawBearerToken()     // ((Jwt) SecurityContextHolder.getContext().getAuthentication().getPrincipal()).getTokenValue() — the validated JWT's raw compact string
```
`getRawBearerToken()` is the token-relay mechanism plan 05-02's outbound HTTP clients (to locations-resources-service, custom-field-service, settings-service) use to forward the CALLING user's own already-validated credential as `Authorization: Bearer <token>` on their own outbound calls — avoiding a second service-account credential for the two broadly-readable downstream services (locations-resources-service's GET is gated by `role_calendar_viewer` — a baseline "can see the calendar at all" gate every real booking-capable user is expected to hold alongside their booking role, mirroring legacy's own layered `accesscalendar`-plus-more gate structure; settings-service's GET requires no specific role at all). **Named decision, scope boundary:** custom-field-service's `GET /custom-fields` is a KNOWN EXCEPTION where token relay alone is insufficient — see plan 05-02's explicit handling of that gap.

`Tier2FailClosedTest.java` — same pattern as every prior-phase service: unreachable issuer → `GET /bookings` with a syntactically-valid bearer token → `503 SERVICE_UNAVAILABLE`; reachable issuer, no `Authorization` header → `401 AUTH_UNAUTHENTICATED`; reachable issuer, authenticated via `jwt()` with no booking roles at all → `POST /bookings` → `403 BOOKING_FORBIDDEN` (not Spring's default whitelabel body).

`Tier1Tier2ConsistencyTest.java` — reads `../api-gateway/src/main/java/com/bookinghub/gateway/config/SecurityConfig.java`'s actual text (same relative-path technique as Phase 3/4's precedent) and asserts: (a) the Gateway's file contains the literal `/bookings/**` pathMatcher with `hasAnyAuthority` naming exactly `role_booking_viewer`, `role_booking_creator`, `role_booking_approver`; (b) via reflection, every `@PreAuthorize` role name on this service's booking controllers (built in plans 05-02/05-03/05-04) is ONE OF those three strings — never a role outside the Gateway's permitted set (this is what "never weaker" means for a coarse Tier-1 gate: Tier-2 may narrow to a subset per action, but must never require/accept a role the Gateway wouldn't have already let through). If the Gateway source file cannot be found at the expected relative path, fail explicitly rather than skip silently. **Cross-reference, matching Phase 3 plan 03-02's `PermissionController` precedent exactly:** plan 05-04's `BookingApprovalController` (approve/deny) deliberately carries NO `@PreAuthorize` annotation at all — it needs the FRD's distinct `APPROVAL_FORBIDDEN` code instead of the generic `BOOKING_FORBIDDEN` this service's `BookingAccessDeniedHandler` produces, so it performs its own manual `currentUserProvider.hasRole("role_booking_approver")` check and throws `ApprovalForbiddenException` directly.
