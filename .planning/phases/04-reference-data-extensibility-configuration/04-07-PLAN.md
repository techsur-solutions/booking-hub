  <action>
Gap from UAT Test 1: The frontend's keycloak.ts falls back to `http://localhost:8180` when `VITE_KEYCLOAK_URL` is unset. The browser cannot reach `localhost:8180` (that's the user's Mac, not the sandbox). Keycloak is running fine at `keycloak:8080` inside the compose network, but the browser needs a public URL.

**The fix:** Add an `environment:` section to the `frontend:` service in docker-compose.yml with:

```yaml
  frontend:
    build: ./frontend
    depends_on:
      - api-gateway
    environment:
      VITE_KEYCLOAK_URL: "http://localhost:8180"
    ports:
      - "3000:80"
```

**Wait, why localhost:8180 if that's the problem?** Because:
1. Vite build-time env vars are baked into the frontend bundle at `docker build` time
2. The compose file maps Keycloak's internal port 8080 to host port 8180: `ports: - "8180:8080"`
3. When the sandbox's preview URL opens `http://<sandbox>.local:3000`, the frontend JS runs in the browser
4. The browser can reach `http://localhost:8180` because **the sandbox's port forwarding makes host port 8180 reachable as localhost from the preview**
5. This is identical to how the frontend reaches the Gateway at `http://localhost:8080` (Gateway's compose ports mapping `- "8080:8080"`)

**Cross-service URL pattern:** Frontend (in browser) → localhost:8180 (Keycloak), localhost:8080 (Gateway). Backend services use internal names (`keycloak:8080`, `api-gateway:8080`). This is the standard compose dev pattern: browser uses localhost + published port, containers use service names.

**Alternative rejected:** Setting `VITE_KEYCLOAK_URL: "http://keycloak:8080"` would NOT work — the browser cannot resolve the service name `keycloak` (it's not on the compose network).

**Build-time vs runtime:** Vite's `import.meta.env.VITE_*` values are replaced at BUILD time by the `docker build` step. The `environment:` block in compose sets the env vars available during the `docker build ./frontend` invocation. For runtime-dynamic URLs (e.g., different per-deployment), you'd need a different pattern (e.g., window-injected config). This is build-time-sufficient for local dev.

Add the `environment:` section directly under the `frontend:` service, above `ports:`.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-07-01 | Spoofing | Keycloak URL in frontend build | accept | Risk: malicious actor who controls docker-compose.yml at build time can redirect login to a phishing endpoint. Owner: deployment environment. Why acceptable: (1) docker-compose.yml is developer-controlled source code, not runtime config; (2) a compromised build environment has broader supply-chain risks than this URL; (3) production deployments must use runtime-injected config with CSP enforcement (deferred to future work). Local dev assumes trusted build environment. |
| T-04-07-02 | Information disclosure | Keycloak URL visible in frontend bundle | accept | Risk: bundle inspection reveals Keycloak endpoint. Owner: architectural constraint. Why acceptable: OIDC requires the client to know the authorization server's public URL by design; the realm's .well-known endpoint is intended to be discoverable. No secrets are exposed (clientId is public, no client secret in PKCE flow). |

</threat_model>
