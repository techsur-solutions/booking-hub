<objective>
Lay the domain and Tier-2 security foundation for settings-service: an additive outbox-table migration (the singleton `settings` table + its seed row already exist from Phase 2 — no schema gap here), a JPA entity mapping to the existing singleton row with no `@GeneratedValue` (enforcing the one-row invariant in code, not just via the DB `CHECK` constraint), the shared error-response contract, and independent Tier-2 JWT re-validation matching the Gateway's exact read/write split.

Purpose: Phase 2 (plan 02-07) scaffolded an empty schema with a pre-seeded singleton row and zero business logic. This plan is the prerequisite domain/security layer plan 04-06's GET/PUT controller builds on top of. settings-service is the simplest of this phase's three services (one row, two endpoints) but is also the one Phase 5's booking-service will depend on synchronously at booking-creation time — getting its foundation right matters disproportionately to its size.
Output: A migrated `settings_db` schema (V1 unchanged + additive outbox table), a `Settings` JPA entity that structurally cannot represent more than one row, a shared error contract, and a Tier-2-secured service proven to exactly match the Gateway's authenticated-read/admin-write split.
</objective>

**Named decision — no schema gap here, unlike locations-resources-service.** TechArch's V1 DDL for the `settings` singleton (already executed by Phase 2 plan 02-07, including its `INSERT INTO settings (id) VALUES (1) ON CONFLICT (id) DO NOTHING` seed) already carries forward exactly the 4 fields this phase's success criteria require: `approve_booking`, `calendar_slot_size`, `calendar_min_time`, `calendar_max_time`. **Named decision — scope is intentionally narrower than legacy's full 33-row settings table** (F0 findings/05-platform-settings.md catalogued all 33 legacy rows across General/Email/Calendar/Locations categories): this migration/system carries forward only these 4 fields as a deliberate scope-narrowing decision — site branding, email config, and the remaining legacy rows are out of scope entirely for this service (cite the full F0 inventory for traceability; this is not a silent omission).

This migration ONLY adds the outbox table:
```sql
CREATE TABLE outbox (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    aggregate_type  VARCHAR(64) NOT NULL,              -- always 'settings' (singleton — no other aggregate type exists in this service)
    aggregate_id    UUID NOT NULL,                      -- a fixed sentinel UUID representing the singleton (not the integer PK — outbox rows need a UUID-shaped aggregate_id for cross-service consistency with every other service's outbox table)
    exchange        VARCHAR(100) NOT NULL,              -- 'settings.events' (already declared, Phase 2 plan 02-09)
    routing_key     VARCHAR(100) NOT NULL,              -- always 'settings.updated' (only one routing key exists for this aggregate)
    idempotency_key UUID NOT NULL DEFAULT gen_random_uuid(),
    payload         JSONB NOT NULL,
    status          VARCHAR(16) NOT NULL DEFAULT 'pending',
    attempt_count   INTEGER NOT NULL DEFAULT 0,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    published_at    TIMESTAMPTZ NULL
);
CREATE INDEX idx_outbox_pending ON outbox (status, created_at) WHERE status = 'pending';
CREATE UNIQUE INDEX uq_outbox_idempotency_key ON outbox (idempotency_key);
```
