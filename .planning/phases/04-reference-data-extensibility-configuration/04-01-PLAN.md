**Named decision — Tier-2 stricter than Tier-1 for reads (deliberate, per the two-tier model):** the Gateway's Tier-1 route table (already built, Phase 2 plan 02-10) requires only "authenticated" for `GET /locations/**`/`GET /resources/**`. TechArch's own API table (§4.3) specifies `accessCalendar` (read) — mapped to `role_calendar_viewer` per the Keycloak realm (Phase 2 plan 02-09) and Phase 3's permission seed. This Tier-2 layer enforces `role_calendar_viewer` specifically for GETs, which is STRICTER than Tier-1's "any authenticated" — this is architecturally correct per the two-tier model (Tier-2 may be stricter, never weaker) and is proven never-weaker by this task's `Tier1Tier2ConsistencyTest`.

`SecurityConfig.java` — `@EnableWebSecurity @EnableMethodSecurity` + `SecurityFilterChain`:

    .requestMatchers("/actuator/health/**").permitAll()
    .anyRequest().authenticated())
.oauth2ResourceServer(oauth2 -> oauth2
    .jwt(Customizer.withDefaults())
    .authenticationEntryPoint(jwksOutageAuthenticationEntryPoint))

Controller methods (built in plan 04-02) carry the actual role requirement via `@PreAuthorize("hasRole('role_calendar_viewer')")` (GET endpoints) / `@PreAuthorize("hasRole('role_location_admin')")` (POST/PUT/DELETE on both Location and Resource — per the Keycloak realm/Phase 3 permission seed's provisional folding of `accessresources` into `role_location_admin`, see plan 04-02's Task 1 for the explicit naming of that decision).

`JwksOutageAuthenticationEntryPoint.java` — same pattern as Phase 3 plan 03-02: implements `AuthenticationEntryPoint`, inspects the cause chain for a network-class JWKS-connectivity failure (`ConnectException`/`UnknownHostException`/`TimeoutException`) → 503 `ApiError` (`SERVICE_UNAVAILABLE`); otherwise → 401 `ApiError` (`AUTH_UNAUTHENTICATED`).

`LocationResourceAccessDeniedHandler.java` — implements `AccessDeniedHandler`. **Simpler than Phase 3's `ApiAccessDeniedHandler`**: this service has exactly ONE admin-forbidden error code (`LOCATION_RESOURCE_FORBIDDEN`, unlike Phase 3's users-permissions-service which needed two different codes across two controllers) — so a single global handler producing `LocationResourceForbiddenException`'s shape (403, `LOCATION_RESOURCE_FORBIDDEN`) is sufficient; no manual per-controller `hasRole` check workaround is needed here, `@PreAuthorize` + this handler is enough.
