`SettingsDtos.java`:
```java
record SettingsUpdateRequest(Boolean approveBooking, Integer calendarSlotSize, LocalTime calendarMinTime, LocalTime calendarMaxTime) {}
record SettingsResponse(boolean approveBooking, int calendarSlotSize, LocalTime calendarMinTime, LocalTime calendarMaxTime, Instant updatedAt, UUID updatedBy) {}
```
(`@JsonProperty` mapped to `approve_booking`/`calendar_slot_size`/`calendar_min_time`/`calendar_max_time`/`updated_at`/`updated_by` per TechArch §4.9's exact shape. Every field in `SettingsUpdateRequest` is optional — a `PUT` may update any subset.)

`SettingsService.java` — `@Service`, injects `SettingsRepository`, `OutboxEventRepository`, `CurrentUserProvider`:
- `getCurrent()`: `settingsRepository.findById(1)` → `SettingsResponse` (the row always exists, pre-seeded by Phase 2 — no not-found case is possible for this singleton).
- `update(request)`: **the upsert-against-fixed-id discipline (F10.3).** Fetches the existing `Settings` row via `findById(1)` (never constructs a new entity with a different id — there is no create path for Settings at all, matching the FRD's explicit "no create/delete endpoints exist for Settings" statement). Applies only the fields present in `request` (partial update — `null` fields are left unchanged). **Server-side validation (defense in depth beyond the DB `CHECK` constraints, point 20 in the phase brief):**
  - if the resulting `calendarMinTime` is not strictly before the resulting `calendarMaxTime` → throw `SettingsInvalidCalendarRangeException` (400) — checked using the POST-merge values (i.e., if only one of the two times is being changed, validate against the OTHER field's current persisted value, not a stale pre-merge pair).
  - if the resulting `calendarSlotSize` is not positive → throw `SettingsInvalidSlotSizeException` (400).
  - Persists the mutated row (`updatedAt = Instant.now()`, `updatedBy = currentUserProvider.getCurrentUserId()`); writes an `OutboxEvent` (`aggregateType="settings"`, `exchange="settings.events"`, `routingKey="settings.updated"`, payload containing the full new state) in the SAME transaction.

**Named decision — immediate propagation, no reload-required quirk (closes F0's confirmed legacy restart-required caching behavior, point 18 in the phase brief).** F0 (findings/05-platform-settings.md) confirmed legacy loads Settings into an in-memory struct ONCE at `onApplicationStart` — a UI-driven settings change has NO runtime effect until the application is reloaded/restarted (confirmed by the legacy controller's own success-flash-message text: "please note you will need to reload the application for this to take effect"). This implementation has NO in-memory cache at all — `getCurrent()` reads the database directly on every call, so a `PUT` is visible to the very next `GET` with zero propagation delay. This is a deliberate, explicitly-named improvement over legacy's confirmed behavior, not a silent divergence. Separately, this service ALSO publishes `settings.updated` (via the outbox, Task 2) for any dependent service (e.g., a future cache-invalidation consumer) that wants an event-driven signal in addition to the always-fresh synchronous read.

`SettingsController.java` — `@RestController`:
- `GET /settings` → no `@PreAuthorize` beyond the class-level `authenticated()` baseline already enforced by `SecurityConfig` (plan 04-05) — any authenticated caller, any role, may read.
- `PUT /settings` → `@PreAuthorize("hasRole('role_settings_admin')")` → 200 `SettingsResponse`.
