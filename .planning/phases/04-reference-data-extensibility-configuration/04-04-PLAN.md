Rather than inventing an uncatalogued error code, handle this via standard Bean Validation instead of a hand-thrown `ApiException`: annotate `CustomFieldUpsertRequest.fieldType` with `@Pattern(regexp = "textfield|select|textarea|radio|checkbox")`, validate the DTO with `@Valid` in the controller, and add `services/custom-field-service/src/main/java/com/bookinghub/customfield/error/GlobalExceptionHandler.java` to this task's file list to add a second `@ExceptionHandler(MethodArgumentNotValidException.class)` method (additive to plan 04-03's existing single-handler file) that shapes the result as a 400 `ApiError` with `error_code="REQUEST_MALFORMED"` — the FRD's own platform-level cross-cutting code (TechArch §4.12) — rather than Spring's default validation-error body. This keeps the FRD's two named codes reserved for exactly the two cases they describe.

**Named decision — context/template model simplification, closing open-questions.md #6's join-model sub-question.** F0 found legacy's model is two-tier: `Customfield.parentmodel` (UI-only enum, `event` or `location`) scopes a field DEFINITION to an entire model type; `Customfieldjoin.customfieldchildid` scopes one stored VALUE to one specific instance — there is NO per-specific-Location definition scoping in legacy at all, only "all events" or "all locations" as a whole. This system's `custom_field_templates.context_id` (nullable UUID) instead references a SPECIFIC Location id directly: `context_id = NULL` means "applies to all bookings globally" (the new-system equivalent of legacy's `parentmodel='event'`), and `context_id = <a Location id>` means "applies only to bookings at that specific Location" — **more granular than legacy's all-locations-blanket scoping**, a deliberate improvement, not a parity claim. This also means the new system drops legacy's separate Location-level custom fields entirely (ROADMAP's success criteria only discuss "booking context"), narrowing scope intentionally.
