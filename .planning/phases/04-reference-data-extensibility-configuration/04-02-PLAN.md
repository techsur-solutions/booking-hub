(Field names `@JsonProperty`-mapped to the TechArch §4.3 snake_case wire shape: `css_class`, `created_at`, `updated_at`, `deleted_at`; `colour`/`description` are this phase's F0-driven additions to TechArch's original `LocationUpsertRequest{name, css_class?, building?, layout?}`.)

`LocationService.java` — `@Service`, injects `LocationRepository`, `OutboxEventRepository`:
- `listActive()`: `locationRepository.findAllByDeletedAtIsNull()` mapped to `LocationResponse[]`.
- `getActiveById(id)`: `findByIdAndDeletedAtIsNull(id)` → `LocationResponse`, else throw `LocationNotFoundException`.
- `create(request)`: validates `name` non-empty → throw `LocationNameRequiredException` (400) otherwise; persists; writes an `OutboxEvent` (`aggregateType="location"`, `exchange="location.events"`, `routingKey="location.created"`) in the SAME transaction.
- `update(id, request)`: `findByIdAndDeletedAtIsNull(id)` else `LocationNotFoundException`; re-validates `name`; persists changes; writes outbox `location.updated`.
- `delete(id)`: **the F4.3/open-questions.md#14 policy implementation.** `findByIdAndDeletedAtIsNull(id)` else `LocationNotFoundException` (already-deleted or never-existed both read as not-found, consistent with the `idx_locations_active` partial index Phase 2 already built); sets `deletedAt = Instant.now()` — **never issues a SQL DELETE, never checks for referencing bookings, never blocks**. Writes outbox `location.deleted`. **Named decision:** this is a deliberate improvement over legacy's confirmed orphan-allow-via-hard-delete behavior (F0 open-questions.md #14) — legacy performed a true hard `DELETE` with zero booking-reference guard; this system instead marks the row deleted and retains it, so existing `bookings.location_id` references (Phase 5) continue to resolve against a real (if flagged-deleted) row rather than a dangling id. There is no 409 `LOCATION_IN_USE` path — deletion always succeeds.

`LocationController.java` — `@RestController`:
- `GET /locations` → `@PreAuthorize("hasRole('role_calendar_viewer')")` → 200 `List<LocationResponse>` (active only)
- `POST /locations` → `@PreAuthorize("hasRole('role_location_admin')")` → 201 `LocationResponse`
- `GET /locations/{id}` → `@PreAuthorize("hasRole('role_calendar_viewer')")` → 200 or `LocationNotFoundException`
- `PUT /locations/{id}` → `@PreAuthorize("hasRole('role_location_admin')")` → 200 `LocationResponse`
- `DELETE /locations/{id}` → `@PreAuthorize("hasRole('role_location_admin')")` → 204

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| client→API | `/locations/**`, `/resources/**` admin write surface — the reference data every future booking will attach to |
| service→message-broker | The outbox relay is this service's only outbound path to RabbitMQ |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-02-01 | Tampering | `LocationService.delete` / `ResourceService.delete` | mitigate | Never issues a SQL DELETE — always sets `deleted_at`, verified by `LocationControllerIntegrationTest`/`ResourceControllerIntegrationTest` scenario 5's explicit post-delete GET assertions, and by Task 1/2's static grep that no `repository.delete(` call exists in either service class |
| T-04-02-02 | Elevation of privilege | `LocationController`/`ResourceController` write methods | mitigate | Every POST/PUT/DELETE requires `role_location_admin` via `@PreAuthorize`, verified against a real non-admin caller by integration test scenario 3, and proven never-weaker-than-Gateway by `Tier1Tier2ConsistencyTest` |
| T-04-02-03 | Repudiation / Denial of service | `OutboxPublisher.relayPendingEvents` | mitigate | A RabbitMQ-unreachable exception leaves the row `pending` (never marks `published` on failure) and increments `attemptCount` — the next scheduled poll retries; verified by `OutboxPublisherTest` against a real Testcontainers broker |
| T-04-02-04 | Information disclosure | `restrict_locations`/`layout` JSONB fields echoed in API responses | accept | These fields store admin-authored, non-secret configuration data (location ids, layout labels) — no PII or credential material ever flows through them; residual risk is the same as any other reference-data field in this system |
</threat_model>
