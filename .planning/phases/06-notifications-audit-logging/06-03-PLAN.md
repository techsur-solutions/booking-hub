<objective>
Lay audit-log-service's Tier-2 security, idempotency-capable schema, and RabbitMQ retry/DLQ infrastructure — mirroring plan 06-01's notifications-service foundation exactly, so plan 06-04's 7-queue consumer and admin controller build on proven infrastructure.

Purpose: Y3-integrations.md mandates idempotent consumption for audit-log-service exactly as it does for notifications-service, but the already-applied V1 DDL only gave `notification_deliveries` an idempotency_key column — this plan closes that gap additively before any consumer logic depends on it, and establishes the same fail-closed Tier-2 posture every other service in this project has.
Output: A Tier-2-secured, idempotency-ready, retry/DLQ-configured audit-log-service scaffold, ready for plan 06-04 to add the 7-queue consumer and the admin-facing filterable `GET /audit-log` endpoint.

**Named decision (idempotency_key schema gap):** `audit_log_entries`' V1 DDL (TechArch §3.3, already applied) has no idempotency tracking column, unlike `notification_deliveries`. Y3-integrations.md is unambiguous that BOTH F8 and F11 consumers must be idempotent. This plan adds an ADDITIVE V2 Flyway migration — `ALTER TABLE audit_log_entries ADD COLUMN idempotency_key UUID NULL` plus a partial unique index — executed by the `audit_migrator` schema-owner role Phase 2 already provisioned separately from the `audit_svc` runtime role the V1 `REVOKE UPDATE, DELETE FROM PUBLIC` grant targets, so immutability is completely untouched. This mirrors the established project convention of every service adding its own V2 migration in the phase that actually needs it (Phase 3's users-permissions-service, Phase 5's booking-service).

**Named decision (admin/ops role reuse):** Identical reasoning to plan 06-01 — `role_audit_viewer` is the only provisioned role fitting F11's "admin (log viewing, legacy Logfiles equivalent)" requirement, and is literally named for this exact purpose (unlike notifications-service's more generic "ops" framing, this one is a clean 1:1 fit).
</objective>

`V2__add_idempotency_key.sql` — additive only, do NOT touch any V1 statement:
```sql
-- Y3-integrations.md mandates idempotent consumption for BOTH F8 and F11, but V1's DDL only
-- gave notification_deliveries an idempotency_key column. This additive migration closes that
-- gap for audit_log_entries. Nullable + partial unique index (not NOT NULL) because this is an
-- additive change to a table whose V1 definition had no such column — going forward every
-- consumer-written row populates it, making it effectively required in practice without a
-- blocking NOT NULL constraint that could reject a hypothetical pre-existing row.
ALTER TABLE audit_log_entries ADD COLUMN idempotency_key UUID NULL;
CREATE UNIQUE INDEX uq_audit_log_entries_idempotency_key ON audit_log_entries (idempotency_key) WHERE idempotency_key IS NOT NULL;
```
This migration is applied by the `audit_migrator` role (Flyway's configured user in `application.yml`, already distinct from the `audit_svc` runtime role) — the V1 `REVOKE UPDATE, DELETE ON audit_log_entries FROM PUBLIC` grant is untouched; `ALTER TABLE ADD COLUMN` is a schema-owner DDL operation, not a row-level UPDATE/DELETE.

`AuditLogEntry.java` — `@Entity @Table(name = "audit_log_entries")`, mapping 1:1 to V1 + this V2 column:
```java

@Column(name="actor_id", nullable=false) UUID actorId;

@Column(name="entity_type", nullable=false) String entityType;
```
