<objective>
Lay notifications-service's Tier-2 security, RabbitMQ retry/DLQ infrastructure, and idempotency-tracking domain layer — everything plan 06-02's consumer business logic needs to build on, proven independently before any `@RabbitListener` exists.

Purpose: TechArch §5.2 requires every backend service to independently re-validate JWTs and fail closed identically to the Gateway; Y3-integrations.md requires every event consumer to be idempotent and to retry-then-DLQ rather than silently drop a message. This plan proves both guarantees exist and work (Tier2FailClosedTest, a buildable retry-configured container factory) before plan 06-02 writes a single line of business logic against them — avoiding the same kind of race Phase 5 plan 05-01 deliberately avoided for its own outbox publisher.
Output: A Tier-2-secured, RabbitMQ-retry-configured notifications-service scaffold with a working `notification_deliveries` JPA layer, ready for plan 06-02 to add consumer/template/SMTP logic.

**Named decision (admin/ops role for F8's `GET /notifications/delivery-status` and `GET /notifications/dead-letter`):** FRD Y1-api.md gates both endpoints as "admin (ops/observability)", but Phase 2's Keycloak realm (11 roles total, see `infra/keycloak/README.md`) provisioned no dedicated "ops" role — the closest, and only plausible, fit is `role_audit_viewer` (the same role F11's `GET /audit-log` uses), since both are read-only operational/observability surfaces and the realm's role catalog is frozen from Phase 2. This plan gates both notifications endpoints with `role_audit_viewer` rather than inventing a new, unprovisioned role.

**Named decision (retry attempt count):** `infra/rabbitmq/README.md` states "3 attempts with 5s/30s/2min backoff". Read as 3 RETRIES following an initial attempt (the natural English reading, and the one that gives exactly 3 distinct backoff values for exactly 3 delay-gaps), this plan configures Spring Retry's `maxAttempts(4)` (1 initial + 3 retries) with a custom `BackOffPolicy` producing the 5s/30s/2min delays between attempts 1→2, 2→3, and 3→4 respectively.
</objective>

`RabbitRetryBackOffPolicy.java` — a small custom `org.springframework.retry.backoff.BackOffPolicy` implementation producing exactly 3 delays (5000ms, 30000ms, 120000ms) across up to 3 retries, holding the delay index in a per-retry `BackOffContext`:
```java
public class RabbitRetryBackOffPolicy implements BackOffPolicy {
    private static final long[] DELAYS_MS = {5_000L, 30_000L, 120_000L};
    public BackOffContext start(RetryContext context) { return new Ctx(); }
    public void backOff(BackOffContext backOffContext) throws BackOffInterruptedException {
        Ctx ctx = (Ctx) backOffContext;
        long delay = DELAYS_MS[Math.min(ctx.index, DELAYS_MS.length - 1)];
        ctx.index++;
        try { Thread.sleep(delay); } catch (InterruptedException e) { Thread.currentThread().interrupt(); throw new BackOffInterruptedException("interrupted", e); }
    }
    private static class Ctx implements BackOffContext { int index = 0; }
}
```

`RabbitConfig.java` — `@Configuration`:
```java
@Bean
public SimpleRabbitListenerContainerFactory rabbitListenerContainerFactory(ConnectionFactory connectionFactory) {
    SimpleRabbitListenerContainerFactory factory = new SimpleRabbitListenerContainerFactory();
    factory.setConnectionFactory(connectionFactory);

    Map<Class<? extends Throwable>, Boolean> retryable = new HashMap<>();
    retryable.put(MissingIdempotencyKeyException.class, false);
    retryable.put(UnresolvableRecipientException.class, false);
    retryable.put(Exception.class, true);
    SimpleRetryPolicy retryPolicy = new SimpleRetryPolicy(4, retryable, true); // 4 total attempts: 1 initial + 3 retries

    RetryOperationsInterceptor interceptor = RetryInterceptorBuilder.stateless()
        .retryPolicy(retryPolicy)
        .backOffPolicy(new RabbitRetryBackOffPolicy())
        .recoverer(new RejectAndDontRequeueRecoverer())  // final-exhaustion/non-retryable path: reject without requeue -> broker's existing x-dead-letter-exchange on the queue routes it to <queue>.dlx -> <queue>.dlq, per infra/rabbitmq/README.md — no new topology declared here
        .build();
    factory.setAdviceChain(interceptor);
    return factory;
}
```

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01-01 | Denial of service / Spoofing | `JwksOutageAuthenticationEntryPoint` | mitigate | Any JWKS-connectivity failure returns 503, never silently treats the request as authenticated — mirrors every other service's fail-closed behavior (Phase 2 Gateway, Phase 3 users-permissions-service), proven by `Tier2FailClosedTest` scenario 1 |

| T-06-01-03 | Denial of service | Unbounded in-process retry blocking a listener thread | accept | A single message's 3 retries (5s+30s+2min = ~2.5 min total blocking) ties up one listener container thread per in-flight redelivery; residual risk (thread-pool exhaustion under a burst of simultaneous transient SMTP failures) is accepted as the FRD's explicitly mandated backoff schedule, not a locally-invented value — tuning concurrency (`listener.simple.concurrency`) is left to ops configuration, not application code |
| T-06-01-04 | Tampering | `MissingIdempotencyKeyException`/`UnresolvableRecipientException` bypassing retry | mitigate | Both are registered non-retryable in `SimpleRetryPolicy`'s exception map specifically so a message that can NEVER succeed (structurally missing data) does not waste 3 retry cycles before reaching the DLQ — the DLQ destination and eventual outcome are identical either way, only the wasted-retry latency differs |
