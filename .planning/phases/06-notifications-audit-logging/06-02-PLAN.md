<objective>
Build notifications-service's actual business logic on plan 06-01's foundation: template rendering + SMTP dispatch for all four event types, a consumer that enforces idempotency/retry/DLQ exactly as F8 specifies, and the two admin-only observability endpoints FRD Y1-api.md names.

Purpose: This is where F8's core guarantee — "every event results in a delivered or retried-to-success notification, with no silent drops" — becomes real, executable code and tests, not description.
Output: A fully working notifications-service: consumes 4 event types across 2 queues, sends real emails via SMTP, tracks delivery status durably, exposes admin-readable delivery-status/dead-letter views.

**Named decision (recipient resolution — closes FRD F8 §Process step 3's `[OPEN QUESTION]` within this plan's scope):** The FRD's interim default is "booking owner only" for booking events and "the requesting user" for `password.reset.requested`. Neither Phase 5's booking-service nor Phase 3's users-permissions-service outbox payload is documented as embedding a resolved account email keyed by owner/user id — and this service is architected (TechArch §2.6) as a "pure RabbitMQ consumer... no synchronous client-facing write API", which this plan extends to mean no NEW synchronous outbound dependency on users-permissions-service either (consistent with the "event-driven decoupling" NFR — a notification failure must never create a new runtime coupling that could itself fail). Therefore recipient resolution reads directly from the event's own payload: `contact_email` for `booking.*` events (the persisted `bookings.contact_email` column Phase 5 plan 05-01 added, carried verbatim into the event payload — the only actual email address available without a new cross-service call) and `email` for `password.reset.requested` (per FRD F8 §Inputs' own literal example: "for password.reset.requested: user email, reset token/link" — the FRD's documented input contract, authoritative over any plan's informal prose). If the expected field is absent or blank, this is FRD F8 Error States' own named failure mode ("Recipient address cannot be resolved... Route to DLQ") — not a bug to work around, the specified behavior.

**Named decision (template content):** Y3-integrations.md states "exact legacy template content is an F0 audit input, not invented here", and no such content audit exists in this project's F0 deliverables. Templates here are minimal, functionally-equivalent (F8.4's "content/intent" bar, not byte-identical legacy replication): subject + body naming the booking title/time/status or the reset link, rendering `location_id` by raw ID (no cross-service name lookup — same no-new-sync-dependency reasoning as recipient resolution above).

`NotificationConsumerService.java` — `@Component`, injects `NotificationDeliveryRepository`, `NotificationTemplateService`, `EmailSenderService`, `ObjectMapper`:
```java
@RabbitListener(queues = "notifications.booking.q")
public void onBookingEvent(Message message, @Header("idempotency_key") String idempotencyKey,
                            @Header(AmqpHeaders.RECEIVED_ROUTING_KEY) String routingKey) {
    processEvent(message, idempotencyKey, routingKey);
}

@RabbitListener(queues = "notifications.passwordreset.q")
public void onPasswordResetEvent(Message message, @Header("idempotency_key") String idempotencyKey,
                                   @Header(AmqpHeaders.RECEIVED_ROUTING_KEY) String routingKey) {
    processEvent(message, idempotencyKey, routingKey);
}

private void processEvent(Message message, String idempotencyKey, String routingKey) {
    if (idempotencyKey == null || idempotencyKey.isBlank()) {
        throw new MissingIdempotencyKeyException("event missing idempotency_key header, routing_key=" + routingKey);
    }
    JsonNode eventData = objectMapper.readTree(message.getBody());
    UUID entityId = extractEntityId(eventData); // eventData.get("id") primary; fall back to a UUID of zeros only if truly absent, logging a warning — never throw here, a missing entity id does not prevent sending the email itself

    NotificationDelivery row = new NotificationDelivery();
    row.setIdempotencyKey(idempotencyKey);
    row.setEventType(routingKey);
    row.setEntityId(entityId);
    row.setStatus("pending");
    row.setAttemptCount(0);
    try {
        notificationDeliveryRepository.saveAndFlush(row); // the authoritative idempotency boundary: a unique-constraint violation here means this idempotency_key was already processed
    } catch (DataIntegrityViolationException alreadyProcessed) {
        log.info("duplicate delivery suppressed for idempotency_key={}", idempotencyKey);
        return; // ack as a no-op — never rethrow, never send a second email
    }

    String recipient = routingKey.equals("password.reset.requested")
        ? textOrNull(eventData, "email")
        : textOrNull(eventData, "contact_email");
    if (recipient == null || recipient.isBlank()) {
        throw new UnresolvableRecipientException("no resolvable recipient for idempotency_key=" + idempotencyKey);
    }

    RenderedEmail rendered = notificationTemplateService.render(routingKey, eventData); // TemplateRenderingException propagates as retryable
    emailSenderService.send(recipient, rendered.subject(), rendered.body());            // MailException propagates as retryable

    row.setStatus("sent");
    row.setAttemptCount(row.getAttemptCount() + 1);
    row.setLastAttemptedAt(Instant.now());
    notificationDeliveryRepository.save(row);
}
```
On a retryable exception (anything other than the two non-retryable types), the row is left at `status='pending'` with `attempt_count=0` from the failed attempt — Spring Retry re-invokes `processEvent` from scratch on the SAME message per plan 06-01's interceptor, and since the row was already inserted, the retry's own `saveAndFlush` will now hit the SAME unique-constraint path and short-circuit as "already processed" even on its own retry! **This is a real bug the implementer must avoid**, not a line to copy literally: split the method so the idempotency INSERT and the send-attempt are not re-executed together on retry. Correct shape: perform the idempotency-insert-or-return-early check ONCE per message (outside what Spring Retry re-invokes), OR — simpler and recommended — look the row up first; if it exists AND `status == 'sent'`, no-op and return; if it exists and `status` is `'pending'`/`'retrying'` (a retry of THIS message), proceed to send without re-inserting, incrementing `attempt_count` and setting `status='retrying'` before the send attempt and `status='sent'` after; if it does not exist, insert it fresh at `status='pending'` then proceed. This existence-check-then-branch is safe from the race the INSERT-only approach would have IF AND ONLY IF the lookup-then-insert pair is the thing Spring Retry re-invokes as a whole (which it is, since the interceptor wraps the entire listener method) — the remaining race (two truly concurrent deliveries of the same redelivered message, not a retry-of-the-same-invocation) is still closed by the unique constraint on `idempotency_key`, caught and treated as "already processed" exactly as before. Implement this corrected lookup-first shape, not the insert-first sketch above.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| broker→consumer | Event payloads are untrusted-shape JSON from another service's outbox relay — a missing/malformed field must never crash the listener thread or silently drop the message |
| consumer→SMTP | This service's one outbound network dependency; a provider outage must degrade to retry/DLQ, never block or corrupt the originating booking/password-reset transaction (already committed upstream) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-02-01 | Tampering / Denial of service | `processEvent`'s JSON parsing of an untrusted event body | mitigate | Malformed/missing fields are checked explicitly (`textOrNull`, required-field checks in `NotificationTemplateService`) and raise typed exceptions routed through the SAME retry/DLQ path as any other processing failure — never an uncaught `NullPointerException`/`JsonProcessingException` that could crash or wedge the listener container |
| T-06-02-02 | Information disclosure | Email body content (booking title/time/location, reset link) | accept | Templates render booking/reset details directly into plain-text email bodies sent only to the resolved recipient address; residual risk (an attacker who intercepts SMTP transport sees booking details) is accepted at the transport-security level (STARTTLS config, `SMTP_STARTTLS` env var) per this architecture's existing integration contract, not newly introduced here |
| T-06-02-03 | Repudiation | `notification_deliveries` row lifecycle | mitigate | Every status transition (`pending`→`sent`/`retrying`/`dead_lettered`) is persisted with `attempt_count`/`last_attempted_at`, giving a durable, queryable record of exactly what was attempted and when — the `GET /notifications/delivery-status` endpoint is this mitigation's observability surface |
| T-06-02-04 | Elevation of privilege | `NotificationStatusController` | mitigate | Relies on plan 06-01's `SecurityConfig` blanket `role_audit_viewer` requirement rather than a route-specific `@PreAuthorize` — verified by this plan's controller test asserting 401/403 for unauthenticated/under-privileged callers |
</threat_model>
