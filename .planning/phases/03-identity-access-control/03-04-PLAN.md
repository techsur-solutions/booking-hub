<objective>
Implement F6's admin-facing and self-service user-management surface: account creation (Keycloak provisioning + local row insert), admin-vs-self read/edit authorization, profile self-editing with a compile-time guard against touching password/role (the structural equivalent of legacy's `structDelete`), and role assignment — publishing `user.created`/`user.updated`/`role.assigned` domain events via the Task-1 outbox for every mutation.

Purpose: This is F6's account-administration half (F6.1/F6.2) plus the F6.5 role-assignment action that feeds F7's permission system. The admin-vs-self authorization split and the password/role-stripping guard are the two places legacy's `Users.cfc` had real, specific security logic worth preserving deliberately rather than re-deriving from scratch.
Output: `UserController`'s 7 endpoints backed by `UserService`, with every account-provisioning and role-change path writing a transactional outbox event — all integration-tested against WireMock + Testcontainers.

**Explicitly out of scope:** legacy's admin "login as" / impersonation capability (`Users.assumeUser()`) is NOT implemented in this phase. F0 Open Question #22 confirmed it exists in legacy but is a UI-only-restricted, server-unenforced security gap (the "assume" link is hidden in the view for admin-on-admin targets, but the controller action itself performs no equivalent check — any `accessUsers` holder could impersonate any other user including another admin). It is also not named among F6's sub-features list in the FRD. This omission is a deliberate scope decision, not an oversight — a future phase may reintroduce impersonation with proper server-side enforcement if product requirements call for it.
</objective>

`UserDtos.java` — one file:
```java
record UserCreateRequest(String email, String initialRole) {}
record UserSelfUpdateRequest(String displayName) {}          // self-service: NO password, NO role field exists on this type at all — the compile-time equivalent of legacy's structDelete
record UserAdminUpdateRequest(String displayName) {}          // admin editing another user's profile-adjacent fields: still no password (Keycloak owns credentials; admin resets via /auth flows or a future dedicated action, not this endpoint) — role changes go through the dedicated roles endpoint, not this one, per FRD's PUT /users/{id} shape ({display_name?}) excluding role
record UserRolesUpdateRequest(List<String> roles) {}
record UserResponse(String id, String email, String displayName, List<String> roles, Instant createdAt, Instant updatedAt) {}
```
Note the FRD's `PUT /users/{id}` request shape (Y1-api.md) is `{display_name?}` only — role changes are a SEPARATE endpoint (`PUT /users/{id}/roles`) for both admin and self paths; this already structurally prevents role-escalation-via-profile-edit without needing a runtime strip, matching (and slightly improving on, via the type system) legacy's `structDelete` approach.

`UserService.java` — `@Service`, injects `UserRepository`, `OutboxEventRepository`, `KeycloakAdminService`, `CurrentUserProvider`, all `@Transactional` on mutating methods (local DB write + outbox write in the SAME transaction, per the outbox pattern):

- `listUsers()`: `userRepository.findAll()` (admin only, enforced at controller layer).
- `createUser(email, initialRole)`: check `userRepository.findByEmailIgnoreCase(email)` first — if present, throw `UserAlreadyExistsException` (409) BEFORE calling Keycloak (cheap fail-fast; avoids provisioning a duplicate Keycloak account for a request that will fail locally anyway). Generate a random initial password (not admin-typed, since this is now an API, not a form — but named decision: **use `temporary=true`** when calling `keycloakAdminService.createUser(...)`, so the new user is prompted to set their own password on first login — this is a deliberate, named IMPROVEMENT over legacy's permanent-admin-set-initial-password-with-no-forced-change behavior, not a parity claim). Insert a local `User` row with `id = <the Keycloak user id returned by createUser>` (never a locally-generated UUID — this is the F0/TechArch `users.id == Keycloak sub` invariant), `email`, `displayName = null`. Write an `OutboxEvent` (`exchange="user.events"`, `routingKey="user.created"`, `payload` containing id/email/initialRole) in the same transaction. Returns `UserResponse`.
- `getUser(targetId)` / `updateUserAsAdmin(targetId, request)`: straightforward repository lookups/updates — authorization (admin-or-self) is the CONTROLLER's job via `@PreAuthorize`/`CurrentUserProvider`, not re-checked here (this method assumes the caller already proved authorization).
- `getOwnProfile()` / `updateOwnProfile(request)`: resolves `currentUserProvider.getCurrentUserId()`, reads/writes that `User` row directly — by construction this can NEVER target another user's row, since the id comes from the validated JWT, not a path parameter. Writes an `OutboxEvent` (`routingKey="user.updated"`) on update.
- `assignRoles(targetId, roles)`: `keycloakAdminService.updateUserRealmRoles(targetId, roles)` (replaces the full role set — see plan 03-02's named decision), then writes an `OutboxEvent` (`routingKey="role.assigned"`, payload containing targetId + the new roles list) in the same local transaction as... there is no local DB row change here (roles live in Keycloak, not the local `users` table), so the outbox write stands alone in its own transaction — still durable/at-least-once via the same outbox-then-relay mechanism, just without a co-located business-row change to pair it with.

`UserController.java` — `@RestController @RequestMapping("/users")`:
- `GET /users` → `@PreAuthorize("hasRole('role_user_admin')")` → 200 `List<UserResponse>`
- `POST /users` → `@PreAuthorize("hasRole('role_user_admin')")` → 201 `UserResponse`
- `GET /users/{id}` → method-level check: `hasRole('role_user_admin') OR currentUserProvider.isSelf(#id)` (Spring Security SpEL referencing the path variable) → 200 `UserResponse`; else 403 `ActionForbiddenException`
- `PUT /users/{id}` → same admin-or-self guard, body `UserAdminUpdateRequest` → 200 `UserResponse`
- `PUT /users/{id}/roles` → `@PreAuthorize("hasRole('role_user_admin')")` strictly (never self, even for one's own roles — legacy had no self-service role-change either) → 200 `UserResponse`
- `GET /users/me` → any authenticated caller → 200 `UserResponse` (always the caller's own)
- `PUT /users/me` → any authenticated caller, body `UserSelfUpdateRequest` (the type with NO password/role fields) → 200 `UserResponse`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| client→API | Every `/users/**` route requires a valid, re-validated (Tier 2) JWT; admin-vs-self is the fine-grained decision made entirely in this plan |
| db→render | `UserResponse` is constructed explicitly field-by-field, never serializing the JPA `User` entity directly — prevents accidental exposure of any future-added sensitive column |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-04-01 | Elevation of privilege | `UserSelfUpdateRequest` (dto/UserDtos.java) | mitigate | The self-service update DTO has NO password or role field at the TYPE level — not a runtime strip of a shared struct (legacy's approach, `structDelete`), but a structurally distinct type the deserializer cannot populate those fields into even if a client sends them in the raw JSON body; verified by `UserControllerIntegrationTest` step 6 |
| T-03-04-02 | Elevation of privilege | `UserController` `GET`/`PUT /users/{id}` | mitigate | Admin-or-self check via `@PreAuthorize` SpEL referencing both the caller's realm role AND `CurrentUserProvider.isSelf(#id)` — a non-admin caller can never reach another user's record; verified by `UserControllerIntegrationTest` steps 4-5 |
| T-03-04-03 | Elevation of privilege | `PUT /users/{id}/roles` | mitigate | Requires `role_user_admin` unconditionally — unlike profile fields, there is no self-service path for one's own roles at all (matching legacy, which had no self-role-change capability either); verified by step 7 |
| T-03-04-04 | Tampering | `users.id` insertion in `createUser` | mitigate | The local `User` row's `id` is set EXCLUSIVELY from the Keycloak user id `KeycloakAdminService.createUser` returns — never a client-supplied or independently-generated value — preserving the `users.id == Keycloak sub` invariant from the first row onward |
| T-03-04-05 | Information disclosure | `UserResponse` construction | mitigate | Hand-assembled from named `User`/role fields, never `@JsonIgnoreProperties`-on-the-entity-and-hope — the entity is never returned directly from any controller method, eliminating an entire class of future accidental-field-leak bugs as the entity evolves |
| T-03-04-06 | Elevation of privilege | Legacy `Users.assumeUser()` (impersonation) | accept (scoped out) | F0 Open Question #22 confirmed this is a server-unenforced legacy gap (UI hides "assume" for admin targets, but the controller performs no equivalent check). Not implemented in this phase at all — there is no impersonation endpoint for this gap to exist IN — residual risk is "feature doesn't exist yet," not "feature exists with a known hole"; a future phase introducing impersonation must build server-side enforcement from the start, not port legacy's gap forward |
</threat_model>
