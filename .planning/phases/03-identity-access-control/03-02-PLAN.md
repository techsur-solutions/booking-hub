<objective>
Give users-permissions-service its own independent Tier-2 JWT validation (defense-in-depth, matching the Gateway's fail-closed-on-JWKS-outage behavior exactly), and a tested Keycloak integration layer — an Admin API wrapper (account provisioning, credential reset, role replacement, forced logout) authenticated as the `userperm-admin-client` service account, plus a direct-grant token client for login/password-verification — so every controller plan 03-03/03-04/03-05 writes can call Keycloak without touching the admin-client library or JWT internals directly.

Purpose: TechArch §5.2 requires every backend service to re-validate tokens itself, never trusting the Gateway's decision alone, and to fail closed identically to the Gateway on IdP outage. This is also the one place in the architecture (per TechArch §5.1) a service calls Keycloak as an administrative actor rather than just validating tokens — isolating that capability here keeps every later controller thin.
Output: A Tier-2-secured service (permitAll only on the genuinely-public auth routes), a `KeycloakAdminService` and `KeycloakTokenClient` fully unit-testable against WireMock (no live Keycloak required), and a `CurrentUserProvider` every later controller uses for self-vs-admin authorization checks.
</objective>

`SecurityConfig.java` — `@EnableWebSecurity @EnableMethodSecurity` + a `SecurityFilterChain` bean:
```java

    .requestMatchers("/auth/login", "/auth/password-reset/request", "/auth/password-reset/complete", "/actuator/health/**").permitAll()
    .anyRequest().authenticated())
```

Public-route list matches exactly the two public `/auth/**` paths from the FRD's Y1-api.md Auth table (login, password-reset request/complete) plus actuator health — NOT `/auth/logout` or `/auth/password-change`, both of which are authenticated.

`JwksOutageAuthenticationEntryPoint.java` — implements `AuthenticationEntryPoint`. On any `AuthenticationException`, inspect the cause chain (`ex.getCause()` recursively) for a network-class failure reaching the JWKS endpoint (`java.net.ConnectException`, `java.net.UnknownHostException`, `java.util.concurrent.TimeoutException`, or Nimbus's `com.nimbusds.jose.proc.BadJOSEException` wrapping an I/O failure specifically — distinguish this from a merely-expired-or-malformed-token `JwtValidationException`, which must still be a plain 401). If a network-class cause is found: write HTTP 503 with an `ApiError` body (`error_code: "SERVICE_UNAVAILABLE"`, matching the Gateway's own fail-closed behavior from Phase 2 plan 02-10). Otherwise: write HTTP 401 with `ApiError` (`error_code: "AUTH_UNAUTHENTICATED"`). This is the Tier-2 mirror of the Gateway's `GatewayFailClosedTest` behavior — the two tiers must never disagree about failing closed.

`KeycloakAdminClientConfig.java` — a `@Configuration` class exposing a `Keycloak` bean (from `org.keycloak:keycloak-admin-client`) built via `KeycloakBuilder.builder().serverUrl(...).realm(...).clientId("userperm-admin-client").clientSecret(...).grantType("client_credentials").build()`, reading every value from the `keycloak.*` properties Task 1 added. This is the ONE place in the service that authenticates as an administrative actor against Keycloak, per TechArch §5.1.

`KeycloakAdminService.java` — `@Service` wrapping `Keycloak.realm(realmName).users()`:
- `String createUser(String email, String initialPassword, boolean temporary, String initialRealmRole)` — builds a `UserRepresentation` (`username=email`, `email=email`, `enabled=true`, `emailVerified=true`), POSTs via `realmResource.users().create(...)`, extracts the new user id from the `Location` response header (`CreatedResponseUtil.getCreatedId(response)`), sets the credential (`CredentialRepresentation` with `type=PASSWORD`, `value=initialPassword`, `temporary=temporary`), assigns `initialRealmRole` via `users().get(id).roles().realmLevel().add(List.of(roleRepresentation))`, returns the id. Throws `UserAlreadyExistsException` (from plan 03-01) if Keycloak responds 409.
- `void resetPassword(String keycloakUserId, String newPassword, boolean temporary)` — `users().get(id).resetPassword(credentialRepresentation)`. Lets a Keycloak-side password-policy rejection (400) propagate as `PasswordPolicyViolationException`.
- `void updateUserRealmRoles(String keycloakUserId, List<String> newRoles)` — **replaces** the user's full realm-role set (remove all currently-assigned realm roles, then add exactly `newRoles`) — an explicit, named decision: legacy's `users.role` was a single string column (one role per user, per F0 audit's User model findings); the new system follows FRD F6.5's "one or more roles" and the `PUT /users/{id}/roles {roles[]}` API contract's array shape, so this method's semantics are REPLACE-the-set, not additive — a deliberate improvement over legacy's single-role model, not a parity claim.
- `void logoutUser(String keycloakUserId)` — `users().get(id).logout()`. Named decision: this revokes ALL of the user's active sessions, not a single targeted one — the `POST /auth/logout` API contract (Y1-api.md) takes no request body/session-identifier, so there is no narrower target to revoke; coarser-than-legacy-equivalent full-logout is the only mechanism this contract supports, and is a reasonable security default (logout means fully signed out everywhere).
- `Optional<String> findUserIdByEmail(String email)` — `users().search(email, true)` (exact match), returns the first result's id if present.

`KeycloakTokenClient.java` — plain HTTP client (Spring `RestClient`) against `{server-url}/realms/{realm}/protocol/openid-connect/token`, NOT using the keycloak-admin-client library (that library is for the Admin REST API, not the token endpoint):
- `record TokenResponse(String accessToken, String refreshToken, long expiresIn)`
- `TokenResponse directGrantLogin(String username, String password, boolean rememberMe)` — POSTs `grant_type=password&username=...&password=...&client_id=...&client_secret=...`, using `userperm-direct-grant-client`'s credentials when `rememberMe=false` and `userperm-direct-grant-remember-client`'s credentials when `rememberMe=true` (the two clients carry different `client.session.max.lifespan` overrides at the realm level — plan 03-03 creates them). Maps a Keycloak `invalid_grant` response to `AuthInvalidCredentialsException` (401).
- `boolean verifyCurrentPassword(String username, String currentPassword)` — attempts `directGrantLogin(username, currentPassword, false)`; returns `true` on success, `false` on `invalid_grant` (catches the same exception the above method throws and converts it to a boolean here — password-change's current-password check needs a boolean, not a thrown 401, since a WRONG current password there means a different error code: `PASSWORD_CHANGE_INVALID_CURRENT`, not `AUTH_INVALID_CREDENTIALS`).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| client→API | Every non-public route on this service now independently re-validates the caller's JWT (Tier 2) |
| service→IdP | This service's own outbound calls to Keycloak's Admin REST API and token endpoint, authenticated with highly-privileged service-account/direct-grant client secrets |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-02-01 | Denial of service / Spoofing | `JwksOutageAuthenticationEntryPoint` | mitigate | Any JWKS-connectivity failure returns 503, never silently treats the request as authenticated or falls through to a default-permit — mirrors the Gateway's `GatewayFailClosedTest` behavior exactly (Phase 2 plan 02-10), so Tier 1 and Tier 2 never disagree on fail-closed posture |
| T-03-02-02 | Information disclosure | `keycloak.admin-client-secret` / direct-grant client secrets | mitigate | All three secrets are read exclusively from environment variables backed by the Kubernetes `Secret` Phase 2 already declared (`KEYCLOAK_ADMIN_CLIENT_SECRET`) plus two new keys plan 03-03 adds to that same Secret — never hardcoded in `application.yml`, never logged (Admin API client library does not log request bodies by default) |
| T-03-02-03 | Elevation of privilege | `KeycloakAdminService.updateUserRealmRoles` | mitigate | This method only ever replaces the REALM role set of the TARGET user id passed by the caller — it is the caller (a later plan's `@PreAuthorize`-guarded controller) that is responsible for proving the caller holds `role_user_admin` before invoking it; this class performs no authorization decision itself, it is a pure Keycloak-API wrapper — authorization is Tier-2 controller-layer responsibility, documented here so later plans don't assume this class double-checks it |
| T-03-02-04 | Spoofing | `KeycloakTokenClient.directGrantLogin` | mitigate | Uses two dedicated confidential, non-public, server-side-only clients (never exposed to a browser) with `directAccessGrantsEnabled=true` — the SPA's own login continues to use PKCE exclusively (Phase 2 §5.1); this direct-grant path exists only so THIS backend can proxy a non-SPA API login and verify a current password, never reachable directly from browser JavaScript |
| T-03-02-05 | Repudiation | `KeycloakAdminService.logoutUser` | accept | Revokes ALL of a user's sessions rather than one targeted session, because the `POST /auth/logout` contract (Y1-api.md) carries no session/refresh-token identifier to target narrowly — residual risk (a legitimate session on another device gets force-logged-out too) is accepted as the safer default and explicitly named in Task 2's action, not a silent behavior |
</threat_model>
