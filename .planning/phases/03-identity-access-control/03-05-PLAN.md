`PermissionDtos.java`:
```java
record PermissionMappingEntry(String legacyFlag, String keycloakRole, Object gatedActions, boolean confirmed) {}
record RolePermissionsResponse(String roleName, List<String> permissionFlags) {}
record RolePermissionsUpdateRequest(List<String> permissionFlags) {}
```

`PermissionService.java` — `@Service`, injects `PermissionRepository`, `OutboxEventRepository`:
- `listPermissions()`: `permissionRepository.findAll()` mapped to `PermissionMappingEntry[]`.
- `getRolePermissions(roleName)`: `permissionRepository.findByKeycloakRole(roleName)` → list of `legacyFlag`s that map to this role → `RolePermissionsResponse`.
- `updateRolePermissions(roleName, requestedFlags)`: **the F7.4/F0-mandated deny-by-default enforcement point.** For EVERY flag in `requestedFlags`: look up `permissionRepository.findByLegacyFlag(flag)`. If the flag does not exist in the table at all → throw `PermissionFlagUndefinedException` (400, `PERMISSION_FLAG_UNDEFINED`). If it exists but `confirmed == false` → ALSO throw `PermissionFlagUndefinedException` — an unconfirmed flag must never be assignable to a role through this endpoint, since doing so would be the exact "silently treat unconfirmed as no restriction" failure mode FRD F7 §Validation explicitly forbids. Only flags that exist AND `confirmed == true` may have their `keycloakRole` column updated to `roleName` (this is how the mapping is "assigned" to a role, matching legacy's per-flag role-checkbox-row editing model — see the F0 audit's "Permissions controller" section: editing happens per-flag, not as a single mass-matrix-edit screen). Writes an `OutboxEvent` (`exchange="permission.events"`, `routingKey="permission.updated"`, payload containing roleName + the updated flag list) in the same transaction as the `permissions` table updates.

**Named decision (F0 Open Question #18 — permission-change propagation timing):** per FRD F7 §Process step 7, this service does NOT implement legacy's "reload required" in-memory-cache quirk (legacy's `application.rbs.permission` struct populated once at `onApplicationStart`). A role-to-permission mapping change here takes effect for a given user the moment their NEXT Keycloak token is issued — this service has no in-memory permission cache to invalidate at all; every `@PreAuthorize` check reads the role directly off the caller's current JWT. This is a deliberate, explicit IMPROVEMENT over legacy's restart-required behavior, named here (not silently diverged) because the F0 audit flagged it as a conscious decision point, not an oversight.

`PermissionController.java` — `@RestController`:
- `GET /permissions` → `@PreAuthorize("hasRole('role_permissions_admin')")` → 200 `List<PermissionMappingEntry>`
- `GET /roles/{role}/permissions` → `@PreAuthorize("hasRole('role_permissions_admin')")` → 200 `RolePermissionsResponse`
- `PUT /roles/{role}/permissions` → `@PreAuthorize("hasRole('role_permissions_admin')")` → 200 `RolePermissionsResponse`; a caller lacking this role gets `403 PERMISSIONS_FORBIDDEN` (the FRD's distinct error code for this specific action, per Y2-errors.md — NOT the generic `ACTION_FORBIDDEN`, so configure the `@PreAuthorize` failure handler for this controller specifically to throw `PermissionsForbiddenException` rather than relying on Spring Security's default `AccessDeniedException` → generic 403 mapping).

`OutboxPublisher.java` — `@Component`, injects `OutboxEventRepository`, `RabbitTemplate`:

```java
@Scheduled(fixedDelayString = "${outbox.poll-interval-ms}")
@Transactional
public void relayPendingEvents() {
    List<OutboxEvent> batch = outboxEventRepository.findTop100ByStatusOrderByCreatedAtAsc("pending");
    for (OutboxEvent event : batch) {
        try {
            MessageProperties props = MessagePropertiesBuilder.newInstance()
                .setHeader("idempotency_key", event.getIdempotencyKey().toString())
                .setContentType(MessageProperties.CONTENT_TYPE_JSON)
                .build();
            rabbitTemplate.send(event.getExchange(), event.getRoutingKey(),
                new Message(event.getPayload().getBytes(StandardCharsets.UTF_8), props));
            event.setStatus("published");
            event.setPublishedAt(Instant.now());
        } catch (AmqpException ex) {
            event.setAttemptCount(event.getAttemptCount() + 1);
            // status stays "pending" — next poll retries; RabbitMQ itself being down delays, never loses, the event (TechArch Y3 Publisher guarantee)
        }
        outboxEventRepository.save(event);
    }
}
```

**Named tech decision (TechArch §5-tech-stack explicitly offers a choice here — "Debezium (Postgres CDC) or a scheduled polling-publisher bean"):** this plan chooses the **scheduled polling-publisher bean**, not Debezium CDC — simpler, zero new infrastructure (no Debezium Connect cluster, no Kafka Connect), and this is the FIRST service in the codebase to implement the outbox relay, setting the precedent other services' future phases should follow unless a specific later service has a volume/latency reason to adopt Debezium instead. Named explicitly here, not silently chosen.

Exchange/routing-key values are read directly off each `OutboxEvent` row (written by plans 03-03/03-04/this plan's Task 1) — this bean declares NO new RabbitMQ topology; it publishes to the exchanges/routing-keys Phase 2 plan 02-09 already declared (`user.events` with `user.created`/`user.updated`/`role.assigned`/`password.reset.requested`, `permission.events` with `permission.updated`) verbatim.
