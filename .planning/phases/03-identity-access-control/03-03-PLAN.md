<objective>
Implement the full F6 authentication surface — login, logout, password-reset request/complete, and self-service password-change — against Keycloak, closing three F0-flagged open decisions along the way: session-timeout values (previously unconfirmable from legacy source), the login-vs-reset-request email-enumeration inconsistency (closed by making both generic), and the reset-token expiry re-check gap (closed by validating at submit time against this service's own `password_reset_tokens` table).

Purpose: This is the user-facing half of F6 that replaces legacy's `Sessions`/`PasswordResets` controllers with Keycloak-backed equivalents, while deliberately NOT replicating legacy's actual behavior where legacy was a confirmed bug (the enumeration inconsistency) or an unconfirmable unknown (the session timeout) — both are named, explicit decisions here, not silent parity claims.
Output: `AuthController`'s 5 endpoints, backed by `AuthService`, plus the realm-level Keycloak configuration (session timeouts, password policy, two direct-grant clients) those endpoints depend on — all integration-tested against WireMock + Testcontainers, no live Keycloak required.
</objective>

(Jackson field naming: use `@JsonProperty` for snake_case wire compatibility with the FRD's documented shapes — `access_token`, `refresh_token`, `expires_in`, `remember_me`, `reset_token`, `new_password`, `current_password`.)

`AuthService.java` — `@Service`, injects `KeycloakTokenClient`, `KeycloakAdminService`, `PasswordResetTokenRepository`, `UserRepository`, `OutboxEventRepository`, `CurrentUserProvider`:

- `login(username, password, rememberMe)`: calls `keycloakTokenClient.directGrantLogin(...)`. On success, decode the returned `access_token`'s `realm_access.roles` claim (use the already-configured `JwtDecoder` bean from plan 03-02's resource-server config — same issuer, so decoding here is consistent, not a second trust domain) to populate `roles[]` in the response. On `AuthInvalidCredentialsException`, let it propagate — this is the SAME generic error regardless of whether the username exists (Keycloak's own `invalid_grant` response does not distinguish unknown-user from wrong-password, so this is naturally generic — no extra work needed to close that half of F0 Open Question #20).

- `logout()`: `currentUserProvider.getCurrentUserId()` → `keycloakAdminService.logoutUser(userId)`. Returns 204.

- `requestPasswordReset(email)`: **F0 Open Question #20 (email-enumeration inconsistency) — closed by making this response generic regardless of outcome, per FRD F6 Outputs' explicit "does not reveal whether the email/username exists" spec.** Look up `userRepository.findByEmailIgnoreCase(email)`. If present: generate a raw UUID token, SHA-256-hash it, insert a `PasswordResetToken` row (`expiresAt = now + 2 hours`, F0-confirmed legacy window preserved), write an `OutboxEvent` row (`exchange="user.events"`, `routingKey="password.reset.requested"`, `payload` containing the user id + the RAW token — the raw value is needed downstream by the notification pipeline to build the emailed link, and this is the only place it ever exists outside the hash) in the SAME transaction as the token-row insert (transactional outbox pattern). If NOT present: do nothing (no row written, no event published) — but the HTTP response is **identical either way**: `202` with a generic acknowledgment body. The controller method must not have any branch that produces a different status/body for found-vs-not-found.

- `completePasswordReset(resetToken, newPassword)`: **F0 Open Question #19 (expiry re-check gap) — closed here.** SHA-256-hash the incoming `resetToken`, look up `passwordResetTokenRepository.findByTokenHash(hash)`. If absent, OR `usedAt != null`, OR `expiresAt.isBefore(now())`: throw `PasswordResetTokenInvalidException` (400) — this is the ONLY validation point this API exposes, so there is no earlier stale check to worry about; re-validate all three conditions every time, never trust a cached/prior check. On success: `keycloakAdminService.resetPassword(user.id, newPassword, false)` (a completed reset should NOT force a further forced-change, matching legacy's "successful reset auto-logs the user in" convenience), mark the token row `usedAt = now()`, return `200`. A Keycloak password-policy rejection propagates as `PasswordPolicyViolationException` (400).

- `changePassword(currentPassword, newPassword)`: `currentUserProvider.getCurrentUserId()` → look up the user's email (needed for the direct-grant verification call, which authenticates by username) → `keycloakTokenClient.verifyCurrentPassword(email, currentPassword)`. If `false`: throw `PasswordChangeInvalidCurrentException` (401) — distinctly different from `AUTH_INVALID_CREDENTIALS`, per the FRD's separate error code for this exact scenario. If `true`: `keycloakAdminService.resetPassword(userId, newPassword, false)`.

- `POST /auth/password-reset/request` → 202 (generic ack body, e.g. `{"message":"If an account exists for that address, a reset link has been sent."}`)
- `POST /auth/password-reset/complete` → 200
- `POST /auth/password-change` → 200 (authenticated)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| client→API | `/auth/login`, `/auth/password-reset/**` are the only genuinely unauthenticated entry points into this entire service |
| webhook→handler | The password-reset-request flow writes an outbox event carrying a sensitive raw token value, consumed downstream by a future notifications-service |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-03-01 | Information disclosure | `AuthService.requestPasswordReset` | mitigate | Single response code/body path regardless of account existence — verified by `AuthControllerIntegrationTest` step 5's structural-equality assertion; closes F0 Open Question #20 in code, not just in the controller's happy-path branch |
| T-03-03-02 | Tampering / Replay | `password_reset_tokens.used_at` | mitigate | `completePasswordReset` checks `usedAt == null` AND `expiresAt.isAfter(now())` on every call and sets `usedAt` atomically on success — verified by `AuthControllerIntegrationTest` step 7's replay assertion; closes F0 Open Question #19 |
| T-03-03-03 | Information disclosure | Raw password-reset token in `OutboxEvent.payload` | accept | The raw (unhashed) token value necessarily exists in the outbox payload so the future notifications-service can build the emailed link — residual risk (anyone with direct DB access to `userperm_db` can read pending outbox rows) is accepted and scoped identically to the existing `notification_deliveries` idempotency-key pattern TechArch already establishes; the `password_reset_tokens.token_hash` column itself never stores the raw value, limiting exposure to the transient outbox row's lifetime until relay (plan 03-05) |
| T-03-03-04 | Spoofing | `userperm-direct-grant-client` / `-remember-client` | mitigate | Both are confidential (secret required), `directAccessGrantsEnabled` only — never `standardFlowEnabled`, so neither can be used for a browser-redirect login; secrets live only in this service's K8s `Secret`, never shipped to the frontend bundle |
| T-03-03-05 | Elevation of privilege | `AuthService.changePassword` | mitigate | Requires a successful `verifyCurrentPassword` direct-grant check before calling the privileged `resetPassword` Admin API operation — an attacker holding a stolen but still-valid access token cannot change the victim's password without ALSO knowing the current password, limiting the blast radius of a leaked bearer token alone |
</threat_model>
