  <name>Task 1: Postgres multi-database init script + docker-compose.yml full-stack wiring</name>
  <files>infra/postgres/init-multi-db.sh, infra/postgres/audit-grants.sh, docker-compose.yml, services/audit-log-service/src/main/resources/application.yml</files>
  <action>
Create `infra/postgres/init-multi-db.sh` (mounted into the Postgres container's `/docker-entrypoint-initdb.d/`, which the official `postgres` image runs exactly once, on first boot against an empty data directory — making re-runs across `docker compose restart` safe no-ops as long as the data volume persists). For each of the 7 "simple" services (`booking`, `locres`, `customfld`, `userperm`, `notif`, `feeds`, `settings` — using the exact database names from TechArch §6.1), create:
```sql
CREATE ROLE <svc>_svc WITH LOGIN PASSWORD '<svc>_svc_pw';
CREATE DATABASE <db_name> OWNER <svc>_svc;
REVOKE ALL ON DATABASE <db_name> FROM PUBLIC;
GRANT ALL PRIVILEGES ON DATABASE <db_name> TO <svc>_svc;
```
(matching each service's `DB_USER`/`DB_NAME` env defaults already set in plans 02-01 through 02-07's `application.yml`/ConfigMaps). This role owns its own database only — it has no grant whatsoever on any other service's database, satisfying "no cross-service database connection string."

For `audit_db` specifically, create the TWO-role split required by `audit_log_entries`'s immutability requirement (TechArch §5.3 "enforced at the Postgres role-permission level, not just application code"):
```sql
CREATE ROLE audit_migrator WITH LOGIN PASSWORD 'audit_migrator_pw';
CREATE DATABASE audit_db OWNER audit_migrator;
REVOKE ALL ON DATABASE audit_db FROM PUBLIC;
GRANT ALL PRIVILEGES ON DATABASE audit_db TO audit_migrator;

CREATE ROLE audit_svc WITH LOGIN PASSWORD 'audit_svc_pw';
GRANT CONNECT ON DATABASE audit_db TO audit_svc;
```
(`audit_svc` gets CONNECT only here — its table-level SELECT/INSERT grant is applied AFTER Flyway creates the table, via a second init step described below, since the table doesn't exist yet at Postgres's first-boot time.)

Amend `services/audit-log-service/src/main/resources/application.yml` to split the single datasource from plan 02-08 into two: a Flyway-only datasource using `FLYWAY_DB_USER:audit_migrator`/`FLYWAY_DB_PASSWORD:audit_migrator_pw` (owns the schema, runs migrations), and the JPA runtime datasource continuing to use `DB_USER:audit_svc`/`DB_PASSWORD:audit_svc_pw` (restricted role, used for all application queries). Use Spring Boot's `spring.flyway.url/user/password` properties (distinct from `spring.datasource.*`) to achieve this — Flyway supports a separate connection from the main datasource specifically for this pattern.

The `audit_svc` table-level grant (SELECT/INSERT only, never UPDATE/DELETE) cannot be applied by the Postgres init script above — `audit_log_entries` doesn't exist until audit-log-service's OWN Flyway migration creates it at application boot, which happens strictly AFTER Postgres's `docker-entrypoint-initdb.d` scripts have already run and finished. Applying it there would silently no-op against a nonexistent table. Instead, create `infra/postgres/audit-grants.sh` — a small standalone script (NOT a `docker-entrypoint-initdb.d` script, not invoked by Postgres at all):
```sh
#!/bin/sh
set -e
psql -h postgres -U audit_migrator -d audit_db -c "GRANT SELECT, INSERT ON audit_log_entries TO audit_svc; REVOKE UPDATE, DELETE ON audit_log_entries FROM audit_svc;"
```
This script is run by a DEDICATED one-shot container in `docker-compose.yml` (a new `audit-grants` service, image `postgres:16` so `psql` is available, volume-mounting this script and `PGPASSWORD=audit_migrator_pw` in its environment), whose `depends_on: { audit-log-service: { condition: service_healthy } }` guarantees it only runs AFTER audit-log-service's Flyway migration has already created the table (Spring Boot Actuator's health check cannot report healthy until the application — including its Flyway migration step — has fully started). `GRANT`/`REVOKE` are naturally idempotent, so this one-shot container safely re-running (or not re-running, since it exits after one execution and compose doesn't restart a completed one-shot service by default) on every `docker compose up` is not a correctness concern. This is the SINGLE mechanism applying this grant — no Postgres-init-script variant, no in-container command-wrapper variant.

Create root `docker-compose.yml` wiring all 12 containers:
- `postgres` (image `postgres:16`, volume `pg-data:/var/lib/postgresql/data` + `./infra/postgres/init-multi-db.sh:/docker-entrypoint-initdb.d/01-init.sh:ro`, healthcheck `pg_isready -U postgres`, NO host port published beyond the default dev convenience of `5432:5432` — acceptable since Postgres itself isn't a "Booking-Hub business service" in the §5.4 sense, but document this as a local-dev-only convenience, not a production pattern).
- `rabbitmq` (image `rabbitmq:3.13-management`, volumes for `./infra/rabbitmq/definitions.json:/etc/rabbitmq/definitions.json:ro` and `./infra/rabbitmq/rabbitmq.conf:/etc/rabbitmq/rabbitmq.conf:ro`, healthcheck `rabbitmq-diagnostics check_port_connectivity`, ports `5672:5672` and `15672:15672` for local management-UI convenience).
- `keycloak` (image `quay.io/keycloak/keycloak:25.0`, `command: start-dev --import-realm`, volume `./infra/keycloak/realm-export.json:/opt/keycloak/data/import/realm-export.json:ro`, env `KEYCLOAK_ADMIN=admin`/`KEYCLOAK_ADMIN_PASSWORD=admin` (local-dev-only, documented), healthcheck via `curl -f http://localhost:8080/realms/bookinghub` (or the Keycloak 25.x management health endpoint), port `8180:8080`.
- Each of the 8 business services: `build: ./services/<name>`, `depends_on: { postgres: { condition: service_healthy }, rabbitmq: { condition: service_healthy } }` (RabbitMQ dependency only for the 5 services with `spring-boot-starter-amqp` on the classpath — booking, notifications, feeds, settings, audit-log, users-permissions per earlier plans; locations-resources and custom-field don't need it yet), `environment:` matching each service's documented `DB_HOST=postgres`/`DB_PORT=5432`/`DB_NAME=<its db>`/`DB_USER`/`DB_PASSWORD`/`RABBITMQ_HOST=rabbitmq` values, **NO `ports:` key at all** (only implicit container-network reachability — this is the mechanism enforcing "no backend service directly externally addressable" at the docker-compose level, mirroring the Kubernetes ClusterIP rule).
- `audit-grants`: image `postgres:16` (no build — uses the same official image for its bundled `psql` client), volume `./infra/postgres/audit-grants.sh:/audit-grants.sh:ro`, `environment: PGPASSWORD=audit_migrator_pw`, `entrypoint: ["/bin/sh", "/audit-grants.sh"]`, `depends_on: { audit-log-service: { condition: service_healthy } }` — this is the one-shot grant-applier described above; it has no `ports:` and is expected to exit 0 shortly after audit-log-service becomes healthy.
- `api-gateway`: `build: ./services/api-gateway`, `depends_on` on keycloak (healthy) and all 8 business services (started, not necessarily healthy — Gateway's own circuit breaker handles transient backend unavailability per its design), `environment: KEYCLOAK_HOST=keycloak, KEYCLOAK_PORT=8080`, `ports: ["8080:8080"]` (the deliberate external exposure).
- `frontend`: `build: ./frontend`, `depends_on: [api-gateway]`, `ports: ["3000:80"]`.

| Boundary | Description |

| sandbox→host (docker) | The compose file controls which containers are reachable from outside the compose network entirely |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-12-01 | Elevation of privilege | `docker-compose.yml` business-service definitions | mitigate | Zero `ports:` entries on all 8 business services — verified by the host-side curl-failure loop in Task 2's `<verify>`, the same invariant Kubernetes enforces via `ClusterIP`-only Services in each prior plan |
