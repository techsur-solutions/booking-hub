Author `infra/rabbitmq/definitions.json` in the RabbitMQ management-plugin definitions-import format (`vhosts`, `exchanges`, `queues`, `bindings`, `policies`), covering the FULL topology from TechArch §7.2 verbatim:

**Topic exchanges** (all `durable: true`):
`booking.events` (publisher: booking-service), `location.events` (publisher: locations-resources-service), `resource.events` (publisher: locations-resources-service), `customfield.events` (publisher: custom-field-service), `user.events` (publisher: users-permissions-service), `permission.events` (publisher: users-permissions-service), `settings.events` (publisher: settings-service).

**Consumer queues** (all `durable: true`, each declared with argument `x-dead-letter-exchange` pointing at a matching `<queue-name>.dlx`):
- `notifications.booking.q` — bound to `booking.events` on routing keys `booking.created`, `booking.approved`, `booking.denied` (per F8.1 — notifications-service does not care about `booking.updated`/`booking.deleted`)
- `audit.booking.q` — bound to `booking.events` on routing key `booking.*` (all five: created/updated/deleted/approved/denied)
- `feeds.booking.q` — bound to `booking.events` on routing key `booking.*` (all five, per TechArch §1.4 feed-projection needs)
- `audit.location.q` — bound to `location.events` on `location.*` (all three)
- `feeds.location.q` — bound to `location.events` on `location.updated` and `location.deleted` only (per §1.4 — feeds only needs to keep `location_name` fresh/removed)
- `audit.resource.q` — bound to `resource.events` on `resource.*` (all three)
- `audit.customfield.q` — bound to `customfield.events` on all six routing keys (`customfield.created/updated/deleted`, `template.created/updated/deleted`)
- `audit.user.q` — bound to `user.events` on `user.created`, `user.updated`, `role.assigned` (NOT `password.reset.requested` — that's notifications-only)
- `notifications.passwordreset.q` — bound to `user.events` on `password.reset.requested` ONLY (per TechArch's explicit table note)
- `audit.permission.q` — bound to `permission.events` on `permission.updated`
- `audit.settings.q` — bound to `settings.events` on `settings.updated`

**Dead-letter infrastructure**: for EACH of the 11 consumer queues above, declare a matching `<queue-name>.dlx` fanout exchange and a `<queue-name>.dlq` durable queue bound to it, so a message that exhausts retries (3 attempts: 5s/30s/2min backoff, enforced in application code from Phase 6 onward — not in this declarative topology) lands in its DLQ rather than being silently dropped, per TechArch §7.2's explicit requirement.

Write `infra/rabbitmq/rabbitmq.conf` enabling the management plugin and setting `management.load_definitions = /etc/rabbitmq/definitions.json` (the path this file will be mounted to in plan 02-12's docker-compose.yml), AND setting `loopback_users.guest = false`. **Why this line is required**: RabbitMQ's default `loopback_users` restriction only permits the built-in `guest` account to authenticate from a connection RabbitMQ itself considers loopback (`127.0.0.1`) — a host-side `curl` reaching the broker through Docker's port-forwarded `15672:15672` mapping is NOT loopback from RabbitMQ's point of view (it arrives from the Docker bridge network), so without this relaxation `guest:guest` would be rejected on every host-side management-API call, including plan 02-12 Task 2's RabbitMQ-topology-loaded verification. This is a local-dev-only relaxation — the same category of exception as the Keycloak seed user's password and the `KEYCLOAK_ADMIN_PASSWORD=admin`/`POSTGRES_PASSWORD` conveniences documented in plan 02-12 — never acceptable in a non-local deployment.

Write `infra/rabbitmq/README.md` documenting the full exchange/queue/binding table above (mirroring TechArch §7.2), noting that `load_definitions` re-applies this file idempotently on every broker restart (RabbitMQ's definitions import is declarative/idempotent — re-declaring an existing exchange/queue with identical arguments is a no-op), and documenting the `loopback_users.guest = false` relaxation as a local-dev-only convenience required for host-side management-API access (e.g. `curl -u guest:guest ... localhost:15672/api/...` from plan 02-12's verification), to be replaced with a dedicated non-guest admin credential before any non-local deployment.
  </action>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-09-01 | Information disclosure | `infra/keycloak/realm-export.json` seed user password / client secrets | accept | Local-dev-only placeholder credentials, explicitly documented in `infra/keycloak/README.md` as requiring rotation before any non-local deployment — residual risk owned by whoever deploys beyond local dev; this is standard practice for a committed realm-export fixture, not a production secret store |
| T-02-09-02 | Elevation of privilege | `userperm-admin-client` service-account roles | mitigate | Service-account client is granted ONLY `manage-users`/`view-users` realm-management roles — not full `admin` — scoping its blast radius to account provisioning/credential-reset, per TechArch §5.1's "the one place in the architecture a service calls Keycloak as an administrative actor" |
| T-02-09-03 | Tampering | RabbitMQ consumer queues | mitigate | Every consumer queue declares `x-dead-letter-exchange`; a message that fails processing is never silently dropped — it lands in a `.dlq`, satisfying F8.2/F11.5's durability requirement at the topology level before any consumer code exists |
| T-02-09-04 | Spoofing | `bookinghub-frontend` public client | mitigate | `publicClient: true` with mandatory PKCE (`S256`) and `directAccessGrantsEnabled: false` — the SPA can never authenticate via resource-owner-password-credentials, only the Authorization Code + PKCE flow, preventing credential-phishing-friendly direct-grant usage |
| T-02-09-05 | Information disclosure / Elevation of privilege | `infra/rabbitmq/rabbitmq.conf` `loopback_users.guest = false` | accept | Relaxes RabbitMQ's default restriction so the built-in `guest:guest` account can authenticate over a Docker port-forwarded (non-loopback) connection — required for plan 02-12's host-side management-API verification to work at all.
