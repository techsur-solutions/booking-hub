```yaml

  port: 8080
spring:
  application:
    name: api-gateway
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: bookings
              uri: http://booking-service:8081
              predicates: [Path=/bookings/**]
              filters: [name: CircuitBreaker, args: {name: bookingCB, fallbackUri: forward:/fallback}]
            - id: locations-resources
              uri: http://locations-resources-service:8082
              predicates: [Path=/locations/**,/resources/**]
            - id: custom-fields
              uri: http://custom-field-service:8083
              predicates: [Path=/custom-fields/**,/field-templates/**]
            - id: auth-users
              uri: http://users-permissions-service:8084
              predicates: [Path=/auth/**,/users/**,/permissions/**,/roles/**]
            - id: notifications
              uri: http://notifications-service:8085
              predicates: [Path=/notifications/**]
            - id: feeds
              uri: http://feeds-service:8086
              predicates: [Path=/feeds/**]
            - id: settings
              uri: http://settings-service:8087
              predicates: [Path=/settings/**]
            - id: audit-log
              uri: http://audit-log-service:8088
              predicates: [Path=/audit-log/**]
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: http://${KEYCLOAK_HOST:localhost}:${KEYCLOAK_PORT:8180}/realms/bookinghub
management:
  endpoints:
    web:
      exposure:
        include: health,info
  endpoint:
    health:
      probes:
        enabled: true
```
(Express the routes in whatever concrete Java/YAML syntax Spring Cloud Gateway 2023.0.x's WebFlux `RouteLocator` requires — the table above is the logical routing contract, not literal YAML; a `RouteLocatorBuilder` `@Bean` in Java is equally acceptable and may be clearer for attaching per-route filters.)

`SecurityConfig.java` — a `SecurityWebFilterChain` bean implementing TWO behaviors:
1. **Public routes bypass authentication** (per TechArch §2.1/§4.11): `/feeds/**`, `POST /auth/login`, `POST /auth/password-reset/**` are permitted without a token.
2. **Every other route requires a valid JWT AND the matching role** from this table (TechArch §4.11 + §5.2):
   - `/bookings/**` → `role_booking_viewer` OR `role_booking_creator`
   - `/locations/**`, `/resources/**` → authenticated for GET; `role_location_admin` for POST/PUT/DELETE
   - `/custom-fields/**`, `/field-templates/**` → `role_customfield_admin`
   - `/users/**` → `role_user_admin` (self-access to `/users/me` is a Tier-2 per-service concern per §5.2, not enforced at the Gateway)
   - `/permissions/**`, `/roles/**` → `role_permissions_admin`
   - `/notifications/**` → `role_audit_viewer` (ops/observability role; no dedicated notif-admin role exists in the §5.2 table)
   - `/settings/**` → authenticated for GET; `role_settings_admin` for PUT
   - `/audit-log/**` → `role_audit_viewer`
3. **Fail-closed on JWKS unreachability** (per TechArch §5.1/§7.1 "hard requirement, not a tunable"): configure a custom `ReactiveJwtDecoder` wrapper (or `AuthenticationWebFilter` entry point) that catches any failure reaching the issuer's JWKS endpoint and responds `503 SERVICE_UNAVAILABLE` with the shared `ApiError` JSON shape — NEVER treats an unverifiable token as valid, and never defaults to permitting the request. (The `ApiError` shape itself is formally wired as the global error-response contract in Task 2 via `GatewayErrorAttributes` — for this task, it's sufficient that the fail-closed handler returns 503 with a body resembling that shape; Task 2 makes it authoritative across every error path.)

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| client→API | Every external request to the platform crosses here first — this is THE primary trust boundary for the entire system |
| Gateway→backend | Internal cluster traffic; Gateway forwards the validated bearer token downstream (token relay) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-10-01 | Spoofing | `SecurityConfig.java` JWT validation | mitigate | Every request's bearer JWT is signature-validated against Keycloak's JWKS via `spring-boot-starter-oauth2-resource-server`'s standard `ReactiveJwtDecoder` — verified by `GatewaySecurityTest`'s no-token→401 and wrong-role→403 assertions |
| T-02-10-02 | Elevation of privilege | `SecurityConfig.java` route-to-role matchers | mitigate | `authorizeExchange` matchers encode the exact TechArch §4.11/§5.2 role requirement per route prefix — a request lacking the minimum role never reaches a backend pod, verified by `GatewaySecurityTest` |
| T-02-10-03 | Denial of service | `GatewayFailClosedTest` JWKS-outage scenario | mitigate | Unreachable JWKS endpoint → `503` for every request regardless of token validity — the architecture never fails open, satisfying TechArch §5.1/§7.1's explicit "hard requirement, not a tunable" |
| T-02-10-04 | Denial of service | `InMemoryRateLimiterFilter.java` | mitigate | Per-client-IP token-bucket limiter returns `429` past a configurable threshold, preventing unauthenticated traffic from consuming unbounded backend compute (also a cost control per TechArch §2.1) |
